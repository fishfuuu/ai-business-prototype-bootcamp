# 第三课教师教案——把模糊业务说成可执行契约

> **核心思想：用追问范式把主管的口语想法追问成可核对的业务、数据与验收约定；先定义正确，再谈实施。**

## 一、课程元数据与定位

| 项目 | 本课设定 |
| --- | --- |
| 学员 | 已完成第二课、掌握视觉重构四步闭环与试衣镜使用的业务主管 |
| 时长 | 90 分钟硬上限：85 分钟主线 + 5 分钟机动 |
| 课堂主成果 | 个人业务定义包 V1：一份统一收敛的业务功能卡，包含业务边界、数据契约、Mock 样例和 1—2 条验收场景 |
| 主管判断成果 | 能回答谁遇到什么问题、为什么要做、目标是什么、边界在哪里、错了有什么风险、怎样算通过、何时必须停 |
| 支撑成果 | `docs/PROJECT_STATE.md` 更新业务定义包状态，只作跨课交接 |
| 数据边界 | 只使用 Mock 或已脱敏数据；不输入真实密钥、账号和业务接口 |
| 正式业务 AI 起点 | L5；本课的 grill-me 是可复用追问 Skill，不因用了 Agent 追问就把业务本身判定为 Agent 场景 |

本课用同一个个人原型串起两条学习线：原型线要求"围绕现有原型的一个主路径，补齐业务逻辑、字段、状态和验收场景"，主管线要求"能回答谁、为何、何时、做到哪、怎样算通过"。两条线分别验收，不能相互抵分。

本课不做：在追问尚未结束时实施全部功能、把所有部门需求一次性写成大而全 PRD、用真实业务数据帮助 Agent"理解得更准确"、判断业务 AI 机会。

开场必须先制造一个可见区别：拍脑门盲开需求错乱 vs 契约冻结后的可核对定义。先让学员看见"定义正确"的价值，再解释五个概念。

## 二、逆向目标、证据与核心概念

### 2.1 目标—活动—证据

| 学习目标 | 课堂活动 | 通过证据 |
| --- | --- | --- |
| 学员能选定一条最需要说清的业务路径，并说明选择理由 | Task 1 路径选择 | 一条路径清楚，且只有一个使用者、一个主要动作 |
| 学员能用 grill-me 依次澄清使用者、目标、边界、风险、验收和停止条件 | Task 2 追问范式 | 3—5 轮单问题追问完成，每轮答案经主管确认 |
| 学员能把已确认决定收敛为业务功能卡，未确认项显式保留 | Task 3 收敛功能卡 | 功能卡包含六大要素；未确认项有明确标注 |
| 学员能固定字段字典、状态、Mock 样例和敏感度 | Task 4 数据契约 | 字段、类型、枚举、Mock 样例和敏感等级完整 |
| 学员能写出 1—2 条可观察的验收场景 | Task 5 验收场景 | 验收场景有给定条件、动作和可观察结果 |

概念分层：核心概念为业务问题边界、追问范式（Grill-Me）、业务契约、数据契约、验收场景；扩展认识为敏感度分级与事前脱敏、结构化输出/类型文件。grill-me Skill 名称、TypeScript 文件名、Git 命令在实操中使用但不升级为核心概念。安全红线横向管理，不占概念名额。

### 2.2 四步概念解析公式

#### 业务问题边界

1. **是什么 / 不是什么**：使用者、触发、问题、目标和明确非目标共同限定本次业务；不是一句话需求，也不是全部部门需求。
2. **机制**：回答谁遇到什么问题、为什么要做、目标是什么、边界在哪里；缺少任何一项都会让后续实施失去锚点。
3. **类比 / 反例**：装修前的户型确认图——在敲墙前必须确认哪些房间在范围内、哪些不在；不能只说"装修一下"就开工。
4. **交接价值**：回指 Task 1—2——主管选定的路径和 grill-me 追问的前两步共同建立了业务问题边界。

#### 追问范式（Grill-Me）

1. **是什么 / 不是什么**：沿未决分支逐题澄清并得到主管确认的追问方法；不是让 Agent 无限提问，也不是一次性抛出所有问题。
2. **机制**：每次只问一个最关键的问题，主管确认后再进入下一题；追问覆盖使用者与问题、目标、边界、风险、验收和停止/升级。
3. **类比 / 反例**：装修开工前的主材确认清单——工长拿着清单逐项确认瓷砖品牌、开关插座数量，每项签字后才敲墙；不是一次把所有问题倒给业主。
4. **交接价值**：回指 Task 2——grill-me 确保业务模糊点被逐个逼平，而不是靠 AI 脑补填充。

#### 业务契约

1. **是什么 / 不是什么**：把 User & Problem、Goal、Boundary、Risk、Acceptance、Stop/Escalation 固定为可执行约定；不是口头共识，也不是大而全 PRD。
2. **机制**：已确认的追问结果收敛为一份业务功能卡，未确认项显式保留；契约一旦冻结，后续实施只能在其范围内选择薄片。
3. **类比 / 反例**：装修合同——口头意图变成书面条款，每条都有明确约定和违约处理；不能只靠"我们说好了"。
4. **交接价值**：回指 Task 3——业务功能卡是主管与 IT 之间的可核对约定，也是第四课薄切片实施的冻结输入。

#### 数据契约

1. **是什么 / 不是什么**：固定字段、含义、类型、枚举、来源状态和 Mock 规则，避免前后口径漂移；不是 TypeScript 工程任务，主管只需核对业务含义。
2. **机制**：为每条业务路径列出字段字典，标注含义、类型、是否必填、Mock 样例和敏感等级；工程师可据此写类型或 Schema。
3. **类比 / 反例**：海关进口商品的标准报关单——商品名称、编码、数量和来源必须统一申报；不能前端叫"工单号"、后端叫"订单号"。
4. **交接价值**：回指 Task 4——数据契约保证前端界面与数据字典匹配，是 IT 交接的物理凭证。

#### 验收场景

1. **是什么 / 不是什么**：用给定条件、动作和可观察结果说明怎样算通过；不只列功能名称，也不依赖主观判断。
2. **机制**：描述前置条件存在时，执行什么动作，应观察到什么结果；遇到数据缺失或规则冲突时触发停止并升级。
3. **类比 / 反例**：工厂流水线的紧急拉绳熔断阀——组装顺畅时按流程运转，发现零部件开裂时拉绳停机并升阶给车间主任。
4. **交接价值**：回指 Task 5——验收场景是主管判断"做对了没有"的依据，也是第四课薄切片验收的来源。

### 2.3 扩展认识概念卡

#### 敏感度分级与事前脱敏（认识级）

数据进入对话和材料前先判断敏感等级（公开/内部/严禁发送 AI），不在泄露后再补救。类比演习炸药箱上的红字警示标签——即使里面装的是演习用的无害沙子，箱子上也必须贴好"高危物品"标签，防止真打仗时工人搬错。教师用 2—4 分钟说明，不设独立通过门槛。

#### 结构化输出/类型文件（认识级）

工程师可把数据契约写成 TypeScript 类型或 Schema；主管只需能核对业务含义，不要求自己写类型文件。原版的 `prototype-contract.d.ts` 和 `prototype-data.ts` 是操作实现手段，不是主管的核心学习任务。

讲解时将五张卡放在同一个装修故事中：先确认户型范围（业务问题边界），再逐项确认主材（追问范式），然后签合同（业务契约），接着填报关单（数据契约），最后约定验房标准（验收场景）。总计控制在 10 分钟左右；不要逐字朗读。

## 三、教学准备与安全边界

### 课前预检

- 第二课原型可用：学员已有一条可操作的业务路径和视觉约束。
- grill-me Skill 可用：确认 `.claude/skills/grill-me/SKILL.md` 或课程指定路径存在且可激活。
- 契约文件模板存在：`docs/BUSINESS_FEATURE_CARD.md` 模板（如课程提供）。
- Git 状态干净或有明确基线节点：教师演示前先 `git status` 确认。
- 助教理解环境问题 3 分钟接管规则，知道 grill-me 未激活时的现场处置方式。

### 实操前只讲四条红线

1. 只用 Mock/已脱敏数据，不输入真实资料、密钥、Token 或账号；不用真实业务数据帮助 Agent"理解得更准确"。
2. 追问未结束前不实施功能；先定义正确，再谈实施。
3. 不把所有部门需求一次性写成大而全 PRD；只围绕一条主路径说清。
4. 文字要求和主管确认是工作约束，不冒充 Workflow/HITL、沙箱或运行时硬控制。

教师不得虚构 `verify-project.ps1` 等课堂能力。实际运行什么，就展示什么证据。

## 四、90 分钟控场主线

| 时间 | 宏观阶段 | 教师动作 | 学员动作 | 阶段证据 |
| --- | --- | --- | --- | --- |
| 0—10 分 | **看见区别，建立模型** | 对比拍脑门盲开需求错乱 vs 契约冻结后的可核对定义；用装修比喻和融合图讲五个概念 | 选定一条最需要说清的业务路径 | 知道本课成果与五者关系 |
| 10—25 分 | **教师完整示范** | 用统一案例串演 Task 1—5，只演方法，不让学员复现 | 观察"选路径→追问→收敛→固定数据→写验收"的完整动作 | 建立整体动作锚点 |
| 25—35 分 | **概念核对与追问范式准备** | 提问核对五张概念卡；确认 grill-me 可激活 | 口头回答卡片；完成路径选择和环境检查 | 概念理解和追问工具就绪 |
| 35—80 分 | **学员实操** | 按 Task 1（约 5 分）→ Task 2（约 15 分）→ Task 3（约 8 分）→ Task 4（约 10 分）→ Task 5（约 7 分）巡视 | 完成路径选择、追问、收敛、数据契约和验收场景 | 个人业务定义包 V1 |
| 80—90 分 | **验收与闭合** | 指导主管最终确认验收场景；检查通过证据；收取随堂题 | 主管确认验收场景、核对证据与答案 | 原型线和主管线分别判定 |

压缩顺序：先取消个别展示，再压缩教师示范；不得删除个人实施、业务验收或主管判断。5 道必答题分散在相应 Task 后完成，最后只检查提交。

## 五、逐 Task 示范、口令、巡视与降级

教师统一案例只走一条路径：以工单看板为例，从选定超时预警路径 → grill-me 追问六大要素 → 收敛为业务功能卡 → 固定字段字典与 Mock → 写出验收场景。每个 Task 均按以下四项执教。

### Task 1：选定最需要说清的一条业务路径

- **教师示范**："从你现有的原型中选一条最需要说清的路径——只选一条，不要把整个部门的需求都搬出来。"展示如何用一句话描述路径的使用者、动作和结果。
- **教师口令**："写下你选的路径名称、使用者、主要动作和预期结果；本轮明确不做的也要写一条。"
- **巡视判断**：是否只有一条路径；路径是否太大（包含多个使用者或多个动作）；是否已经在追问前就开始实施。
- **失败降级**：路径太大时缩到一个使用者、一个动作；选不出来时选模糊度最高的一条；已在实施时立即停止，回到定义阶段。

### Task 2：用 grill-me 依次澄清六大要素

- **教师示范**：激活 grill-me，展示一次只问一个问题的追问流程。沿使用者与问题 → 目标 → 边界 → 风险 → 验收 → 停止/升级依次澄清，每轮主管确认后再进入下一题。
- **教师口令**：下发 grill-me 发起提示词模板（见学员指南 Task 2）。
- **巡视判断**：是否一次只问一个问题；主管是否逐轮确认；Agent 是否在追问过程中修改文件；是否已偏离到实施。
- **失败降级**：Agent 一次抛出多个问题时发送救援指令：`请重新读取并严格遵循 grill-me 的物理指令，一次只问我一个问题！`；Agent 擅自修改文件时立即停止，要求列出真实动作。

### Task 3：收敛为业务功能卡，未确认项显式保留

- **教师示范**：展示如何把已确认的追问结果汇总为业务功能卡预览。强调 Task 3A 只读预览门禁——先输出方案预览，等待主管授权后再落盘。未确认项必须显式标注"待确认"，不能悄悄删除。
- **教师口令**：下发业务功能卡汇总预览提示词模板（见学员指南 Task 3）。在收到"同意方案，请开始落盘功能卡与契约资产"前不修改文件。
- **巡视判断**：功能卡是否包含六大要素；未确认项是否显式保留；HITL 只读预览门禁是否被跳过；Agent 是否未经授权就写文件。
- **失败降级**：Agent 未经授权写文件时停止，回退到只读预览；未确认项被悄悄删除时要求补回"待确认"标注；功能卡缺少要素时补齐。

### Task 4：固定字段字典、状态、Mock 样例和敏感度

- **教师示范**：下发数据契约卡提示词模板，展示如何填写字段名称、业务含义、数据类型、是否必填、数据来源、示例值和敏感等级。强调敏感度是写给未来 IT 部门的生产网关脱敏规约。
- **教师口令**：下发数据契约卡提示词模板（见学员指南 Task 4）。
- **巡视判断**：字段字典是否与业务功能卡一致；敏感等级是否标注（公开/内部/严禁发送 AI）；Mock 样例是否与字段类型匹配；是否把 TS 类型文件写成主管核心任务。
- **失败降级**：字段与功能卡漂移时重新对齐；敏感度未标注时补标；学员纠结 TS 语法时提醒"主管核对业务含义，工程师写类型"。

### Task 5：写出 1—2 条可观察的验收场景，主管最终确认

- **教师示范**：展示如何用给定条件、动作和可观察结果写出验收场景。演示主管最终确认：逐项对照功能卡和数据契约，确认或打回。完成后同步 `PROJECT_STATE.md` 和 Git 提交。
- **教师口令**：下发验收场景提示词模板（见学员指南 Task 5）。主管确认后运行 `git add . && git commit -m "feat: complete lesson 3 business definition package V1"`。
- **巡视判断**：验收场景是否可观察（有具体条件、动作和结果）；是否追溯到功能卡；是否只有 1—2 条而非全面铺开；主管是否做了最终确认。
- **失败降级**：场景不可观察时改写为具体条件；场景过多时只保留 1—2 条；主管未确认时补做确认环节。

## 六、现场 Debug 与降级预案

| 问题类型 | 教师处置 | 禁止说法 |
| --- | --- | --- |
| grill-me 未激活，Agent 一次抛出多个问题 | 发送救援指令要求重新读取 Skill，一次只问一个问题 | "AI 就是这样问的，正常" |
| 追问过程中 Agent 擅自修改文件 | 立即停止，要求列出真实动作和改动，回到只追问不实施 | "边问边改效率更高" |
| 页面提示字段未定义 | 核对数据契约字段字典与 Mock 样例是否一致 | "AI 会自动补字段" |
| AI 尝试运行 `cd` 切换目录 | 提醒保持在工程根目录，禁止执行 `cd` 指令 | "cd 一下没关系" |
| 学员选了太大路径无法在课内完成 | 缩到一个使用者、一个动作；未完成部分记入 `PROJECT_STATE.md` | "把所有需求都写完才算通过" |

## 七、随堂测试、通过标准与课后任务

### 两条线分别通过

- **原型线**：业务定义包 V1 包含业务边界、数据契约、Mock 样例和 1—2 条验收场景；字段、规则和验收场景能相互追溯。
- **主管线**：能回答谁、为何、目标、边界、风险、怎样算通过和何时必须停；能指出至少一个停止或升级条件。
- `PROJECT_STATE.md` 只作交接，不能抵消任何一条主线的未通过。

### 必答题（5 题）

1. 业务问题边界需要回答哪五个问题来限定本次业务？
2. grill-me 追问和让 AI 无限提问有什么本质区别？
3. 业务契约固定了哪六个要素？未确认项应该怎么处理？
4. 数据契约要求主管核对什么？TS 类型文件由谁来写？
5. 验收场景和功能名称列表有什么区别？写出一条验收场景需要哪三个部分？

参考要点：使用者/触发/问题/目标/非目标；逐题澄清并确认，不是无限提问；User&Problem/Goal/Boundary/Risk/Acceptance/Stop-Escalation，未确认项显式保留；核对业务含义，工程师写类型；给定条件/动作/可观察结果，不只列名称。

### 拓展题（选做，2 题）

1. 用"装修主材确认清单"比喻解释业务问题边界和业务契约的关系。
2. 如果学员在追问过程中发现一条路径无法说清，应该怎么处理？为什么不能直接让 AI 脑补？

### 课后任务

10—15 分钟：在 `PROJECT_STATE.md` 中补齐业务定义包状态和下一课输入说明。不继续开发功能；第四课只能在该范围内选择一个薄切片实施。
