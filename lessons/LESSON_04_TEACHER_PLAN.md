# 第四课教师教案——把契约切成一个可实施的薄片

> **核心思想：第三课负责把事情说对，第四课负责把一小件事情做对；不把两课挤成一节超载课。**

## 一、课程元数据与定位

| 项目 | 本课设定 |
| --- | --- |
| 学员 | 已完成第三课、掌握业务定义包 V1（业务功能卡 + 数据契约 + 验收场景）的业务主管 |
| 时长 | 90 分钟硬上限：85 分钟主线 + 5 分钟机动 |
| 课堂主成果 | 可验证薄切片候选：一个肉眼可见、可操作、可验收的变化，附契约追溯、状态说明和版本证据 |
| 主管判断成果 | 能裁定切片是否足够小又足够完整，能区分业务状态与技术状态，并在实施前后分别确权 |
| 支撑成果 | `docs/PROJECT_STATE.md` 更新薄切片候选与处置记录，只作跨课交接 |
| 数据边界 | 只使用 Mock 或已脱敏数据；不输入真实密钥、账号和业务接口 |
| 正式业务 AI 起点 | L5；本课的 Agent 是实施原型的开发 Agent，Plan & Execute 是开发协作方式，不等于学员业务已经适合 Agent 化 |

本课用同一个个人原型串起两条学习线：原型线要求"从业务定义包中确认可验收路径并写清本轮边界，由 Skill 自动切分计划后完成可见实施，保留正常、空或失败状态中的必要证据"，主管线要求"能裁定切片是否足够小又足够完整，能区分业务状态与技术状态，并在实施前后分别确权"。两条线分别验收，不能相互抵分。

本课不做：同时实施多个业务切片、要求主管手工掌握 staging/commit/CLI、在尚未理解业务环节时强加 AI 功能、判断业务 AI 机会。

开场必须先制造一个可见区别：巨石一口气盲开导致白屏崩溃 vs 薄切片受控实施后可见、可验收的变化。先让学员看见"小而完整"的价值，再解释四个概念。

## 二、逆向目标、证据与核心概念

### 2.1 目标—活动—证据

| 学习目标 | 课堂活动 | 通过证据 |
| --- | --- | --- |
| 学员能校验第三课契约并确认可独立验收的路径 | Task 1 契约校验与可验收路径确认 | 可验收路径清单可追溯到功能卡和验收场景 |
| 学员能写清本轮做什么和不做什么，为 Skill 自动切分提供边界 | Task 2 边界声明与非目标 | 本轮边界明确写出；非目标至少一条 |
| 学员能激活 Skill 自动生成 Plan，核对后才授权 Execute | Task 3 Skill 自动生成 Plan 与主管核对授权 | Skill 自动输出 3—5 步计划；主管在授权前核对了字段、状态、修改范围和验收路径 |
| 学员能实施一个可见变化并展示两种必要状态 | Task 4 受控实施 | 变化肉眼可见；至少展示两种状态（如正常和空或失败） |
| 学员能按契约验收并记录候选版本与处置结果 | Task 5 主管验收与处置 | 验收追溯到契约；候选实现与主管处置分别留痕；不自动宣称通过 |

概念分层：核心概念为薄切片、版本证据与回退、技术状态与业务状态、可追溯验收；Plan & Execute、两阶段版本记录、有界恢复为操作方法；HITL 授权点为扩展认识。工作区/工作树（Working Tree）、Git 命令、`prototypeState` 调试器在实操中使用但不升级为核心概念。

### 2.2 四步概念解析公式

#### 薄切片

1. **是什么 / 不是什么**：薄切片（纵向业务切片）：每次只做一条“从输入到看到结果”的最小闭环，既不搞一口气全写完的巨石工程，也不做改了半天看不见效果的技术碎片。
2. **机制**：从业务定义包中选择一个可独立验收的纵向变化，只实施这一条；切片虽小但从输入到结果完整。
3. **当课操作例子与边界**：Task 1—2 只选择一条可独立验收的纵向变化；没有完整输入到结果的路径，就不是薄切片。
- **帮助理解的类比（可选）**：像餐厅开业前的试菜：先选一道招牌菜完整做出来（从洗菜、炒菜到端盘试吃闭环检验味道），而不是把整桌满汉全席的所有蔬菜都洗好切好（横向半成品），却一口熟菜都没吃到。薄切片必须是一条纵向贯通、能尝到味道的最小业务闭环。
4. **交接价值**：回指 Task 1—2——主管确认的可验收路径和本轮边界为 Agent 切分计划提供了范围约束；切片虽由 Skill 自动切分，但必须落在主管声明的边界内，且只有一个主要变化。

#### 版本证据与回退

1. **是什么 / 不是什么**：识别 Working Tree、Diff、Commit 如何记录变更和版本证据；不是业务审批，也不规定提交次数。
2. **机制**：激活 incremental-implementation Skill 后，Skill 读取契约文件自动把需求切成 3—5 个独立步骤并落盘计划；主管核对每步的字段、状态、修改范围和验收路径后才授权 Execute；适合目标明确但步骤较多的任务。
3. **当课操作例子与边界**：Task 3 只核对并授权实施计划，Task 5 才把实际变化关联到版本证据；计划本身不是版本记录，版本记录也不是业务批准。
- **帮助理解的类比（可选）**：像办公文档的草稿、修订痕迹和归档版本：Working Tree 是正在编辑的草稿，Diff 显示改了什么，Commit 保存可回看的版本节点。归档版本仍不等于业务审批。
4. **交接价值**：回指 Task 3——主管在授权前必须核对计划，确认无误后才让 Agent 执行；这是第五课 Agent 控制流矩阵的铺垫。

#### 技术状态与业务状态

1. **是什么 / 不是什么**：加载、错误等系统状态和待处理、已升级等业务含义是两件事；不能混为一谈，也不能用技术状态冒充业务状态。
2. **机制**：技术状态（页面卡不卡、报不报错）与业务状态（审批中、已驳回、已完成）是两码事。页面能顺利打开，绝不等于业务逻辑已经走通。
3. **当课操作例子与边界**：Task 4 分别展示加载、空数据、报错等技术状态和草稿、待处理、已完成等业务状态；页面能打开不代表业务已通过。
- **帮助理解的类比（可选）**：像网购的"物流状态"和"商品交易状态"：包裹装车/派送中是物流流转（技术状态），订单已付款/已退款是买卖履约（业务状态）。快递按时送达（技术成功）不等于商品无瑕疵（业务通过）。
4. **交接价值**：回指 Task 4——学员在实施切片时至少展示两种必要状态，并能指出哪个是技术状态、哪个是业务状态。

#### 可追溯验收

1. **是什么 / 不是什么**：把验收场景、操作、观察、原始证据、结论和责任关联到具体版本；不是口头验收、只存截图或把测试通过当业务批准。
2. **机制**：用 Working Tree、Diff 或 Commit 记录实际变更，把候选实现、验收证据和主管处置关联；提交次数由项目需要决定。
3. **当课操作例子与边界**：Task 5 同时保存实际变化和主管处置；两者都要可追溯，但不要求两个 Commit。
4. **交接价值**：回指 Task 5——主管验收后分别留痕候选实现和处置结果，不把两者压成一次自动通过。

### 2.3 操作方法

Plan & Execute、两阶段版本记录、有界恢复是操作方法或安全规程，不是核心概念卡。恢复必须知道范围、证据和责任人，不把危险命令当课堂口令；切片报错时导出 `.patch` 快照备份后恢复 Working Tree Clean，不是无差别清空。

### 2.4 扩展认识概念卡

#### 人在回路授权门禁（HITL）授权点（认识级）

在范围、实施和验收处由人作决定；本课以动作实践，不扩成理论课。Agent 在每个关键节点等待主管口令授权：`同意保存实施计划`、`确认完成 Step 1`、验收通过或打回。教师用 2—4 分钟说明，不设独立通过门槛。

讲解时直接沿 Task 1—5 的真实动作讲四张核心卡：先选一条薄片，再核对实施计划和版本证据，区分两类状态，最后按验收场景逐项核对并留痕。总计控制在 10 分钟左右；不要逐字朗读。

## 三、教学准备与安全边界

### 课前预检

- 第三课契约可用：学员已有 `docs/BUSINESS_FEATURE_CARD.md`、数据契约和 1—2 条验收场景。
- `/incremental-implementation` Skill 可用：确认课程指定路径存在且可激活。
- Working Tree 处于 Clean 状态：教师演示前先 `git status` 确认 `nothing to commit, working tree clean`。
- 开发服务器可启动：双击 `start-project.bat` 或运行 `npm run dev`，本地预览 `http://127.0.0.1:8888/` 可访问。
- 助教理解环境问题 3 分钟接管规则，知道契约不一致时的现场处置方式。

### 实操前只讲四条红线

1. 只用 Mock/已脱敏数据，不输入真实资料、密钥、Token 或账号。
2. 不同时实施多个业务切片；一次只做一个可验证的薄片。
3. 不要求主管手工掌握 staging、commit 或 CLI；Git 操作由 Agent 执行，主管负责核对和授权。
4. 文字要求和主管确认是工作约束，不冒充 Workflow/HITL、沙箱或运行时硬控制；Git 本身不理解业务确权。

教师不得虚构 `verify-project.ps1` 等课堂能力。实际运行什么，就展示什么证据。

## 四、90 分钟控场主线

| 时间 | 宏观阶段 | 教师动作 | 学员动作 | 阶段证据 |
| --- | --- | --- | --- | --- |
| 0—10 分 | **看见区别，建立模型** | 对比巨石一口气盲开白屏 vs 薄切片受控实施；用 Task 1—5 动作链和融合图讲四个概念 | 校验第三课契约，确认可验收路径 | 知道本课成果与四者关系 |
| 10—25 分 | **教师完整示范** | 用统一案例串演 Task 1—5，只演方法，不让学员复现 | 观察"校验→确认路径→写边界→Skill 生成 Plan 核对→实施→验收"的完整动作 | 建立整体动作锚点 |
| 25—35 分 | **概念核对与切片准备** | 提问核对四张概念卡；确认 Working Tree Clean | 口头回答卡片；完成环境检查和契约校验 | 概念理解和环境就绪 |
| 35—80 分 | **学员实操** | 按 Task 1（约 5 分）→ Task 2（约 5 分）→ Task 3（约 10 分）→ Task 4（约 15 分）→ Task 5（约 10 分）巡视 | 完成契约校验、边界声明、Plan 核对、实施和验收 | 可验证薄切片候选 |
| 80—90 分 | **验收与闭合** | 指导主管最终验收；检查通过证据；收取随堂题 | 主管验收、记录处置、核对证据与答案 | 原型线和主管线分别判定 |

压缩顺序：先取消个别展示，再压缩教师示范；不得删除个人实施、业务验收或主管判断。5 道必答题分散在相应 Task 后完成，最后只检查提交。

## 五、逐 Task 示范、口令、巡视与降级

教师统一案例只走一条路径：以工单看板为例，从校验第三课契约 → 确认可验收路径并写本轮边界 → 激活 Skill 自动生成 Plan 主管核对 → 实施可见变化展示两种状态 → 主管按契约验收并记录处置。每个 Task 均按以下四项执教。

### Task 1：校验第三课契约，确认可独立验收的路径

- **教师示范**："先打开你的业务功能卡和数据契约，看看哪些路径可以独立验收。"展示如何从验收场景中确认可验收路径——每条路径有从输入到结果的完整业务结果，能追溯到验收场景。强调这里只确认路径，不手动切分切片；切分由后续 Skill 自动完成。
- **教师口令**："确认 2—3 条可独立验收的路径，每条写清从输入到结果的完整路径和可验收的方式。先不要实施，也不要手动切分切片。"
- **巡视判断**：可验收路径是否追溯到第三课契约；是否从输入到结果完整；是否拆成了没有业务结果的技术碎片；是否越位手动切分切片。
- **失败降级**：路径与契约脱节时回到功能卡重新对齐；拆太碎时合并为一条有业务结果的纵向变化；学员开始手动切分切片时提醒"切分交给 Skill，你只确认路径"。

### Task 2：主管写本轮做什么和不做什么

- **教师示范**："你不需要自己选切片——切分是 Skill 的事。你要做的是写清本轮的边界：做什么、不做什么、不做到哪里。"展示如何写清本轮边界声明：明确本轮聚焦的可验收路径、要实施的主要变化，以及明确不做的部分。这条边界就是给 Skill 自动切分计划时的范围约束。
- **教师口令**："写下本轮聚焦的可验收路径、本轮做什么、本轮明确不做。至少一条非目标。这条边界会交给 Skill，让它在这个范围内自动切分计划。"
- **巡视判断**：本轮边界是否聚焦在一条可验收路径上；非目标是否明确写出；边界是否太宽（包含多个主要变化）或太窄（没有业务结果）。
- **失败降级**：边界太宽时缩到一个主要变化；非目标模糊时追问"不做什么"；学员试图手动选切片时提醒"你写边界，Skill 来切分"。

### Task 3：激活 Skill 自动生成 Plan（增量实施范式），主管核对后才授权 Execute

- **教师示范**：激活 `/incremental-implementation`，展示 Skill 读取契约文件后自动把需求切成 3—5 个步骤并落盘 `IMPLEMENTATION_PLAN.md`。强调切分是 Skill 做的，不是学员手动选的；主管的角色是核对：字段、状态、修改范围和验收路径是否与 Task 2 声明的边界一致。核对无误后发送 `同意保存实施计划`。
- **教师口令**：下发增量实施提示词模板（见学员指南 Task 3）。在收到主管授权前，Agent 不修改代码。
- **巡视判断**：Skill 是否自动生成了计划而非等学员手动切分；主管是否核对了字段、状态、修改范围和验收路径；计划是否落在 Task 2 声明的边界内；是否跳过核对直接授权。
- **失败降级**：Agent 抬手就写代码时停止，要求先激活 Skill 出计划；主管未核对就授权时退回核对环节；计划超出 Task 2 边界时退回 Task 2 重新声明；计划与契约不一致时回到 Task 1 校验。

### Task 4：实施一个可见变化，至少展示两种必要状态

- **教师示范**：发送 `确认完成 Step 1`，展示 Agent 执行一个受控切片。在本地预览中展示至少两种状态（如正常和空，或正常和错误）。使用 `prototypeState` 调试按钮切换技术状态，同时指明业务状态标签。
- **教师口令**：下发授权执行口令（见学员指南 Task 4）。实施后报告实际修改文件和验收方法。
- **巡视判断**：变化是否肉眼可见；是否展示了至少两种状态；学员能否指出哪个是技术状态、哪个是业务状态；Agent 是否只在授权范围内修改。
- **失败降级**：变化不可见时检查是否真的实施了代码；只有一种状态时补展示另一种；学员混淆技术状态和业务状态时回到 Task 4 分别指出页面状态和业务对象状态；Agent 扩大范围时立即停止。

### Task 5：主管按契约验收，记录候选版本与处置结果

- **教师示范**：你在第二课学过用前后对比留下视觉证据，现在用同样的习惯为薄切片留下实施前后的页面证据——验收本身仍按第三课契约追溯。展示主管验收——逐项对照第三课验收场景，确认或打回。验收后记录实际版本变化与主管处置，核对 Working Tree 状态，不以提交次数替代验收。
- **教师口令**：下发验收与版本证据提示词模板（见学员指南 Task 5）。主管确认后核对 `git status` 与处置记录。
- **巡视判断**：验收是否追溯到契约；候选实现与主管处置是否分别留痕；是否自动宣称通过；Working Tree 是否恢复 Clean。
- **失败降级**：验收不通过时记录问题而非强行通过；切片报错时导出 `.patch` 快照后恢复 Clean，下发 `同意记录 Step 1 问题`；不以提交数量替代验收。

## 六、现场 Debug 与降级预案

| 问题类型 | 教师处置 | 禁止说法 |
| --- | --- | --- |
| 契约不一致（`CONTRACT_ASSET_MISMATCH`） | 回退到第三课，核对功能卡与数据契约字段是否匹配 | "AI 会自动修复契约" |
| 切片报错，Working Tree 一直 Dirty | 下发 `同意记录 Step 1 问题`，导出 `.patch` 快照后恢复 Clean | "改坏了就重来" |
| Agent 抬手就写代码，不出计划 | 立即停止，要求先出计划再等授权 | "边想边改效率更高" |
| Agent 一次修改多个切片的文件 | 立即停止，回到 Task 2 声明的边界范围 | "多改几个一起验收" |
| 学员混淆技术状态和业务状态 | 回到 Task 4，分别指出页面状态和业务对象状态 | "Loading 就是待处理" |

## 七、随堂测试、通过标准与课后任务

### 两条线分别通过

- **原型线**：切片从输入到结果完整，但范围只有一个主要变化；变化能追溯到第三课契约和验收场景；至少展示两种必要状态。
- **主管线**：能指出至少一个技术状态和一个业务状态；候选实现与主管处置分别留痕；不自动宣称通过。
- `PROJECT_STATE.md` 只作交接，不能抵消任何一条主线的未通过。

### 必答题（5 题）

1. 薄切片和把任务拆成技术碎片有什么区别？一条合格的薄切片从哪里到哪里完整？
2. Plan & Execute 要求主管在授权 Execute 前核对什么？为什么不能跳过核对？
3. 技术状态和业务状态有什么区别？各举一个例子。
4. 候选实现与主管处置如何分别留痕？为什么提交次数不能替代业务验收？
5. 主管验收不通过时应该怎么处理？为什么不能自动宣称通过？

参考要点：从输入到结果的纵向变化，不是技术碎片；核对字段/状态/修改范围/验收路径；加载/错误/空是技术状态，待处理/已完成是业务状态；Git 不理解业务确权；记录问题而非强行通过，候选与处置分别留痕。

### 拓展题（选做，2 题）

1. 版本控制能提供哪些证据？为什么 Git 记录不等于主管业务批准？怎样把验收关联到具体版本？
2. 如果切片实施后发现第三课契约有遗漏，应该怎么处理？为什么不能直接让 Agent 脑补补齐？

### 课后任务

10—15 分钟：在 `PROJECT_STATE.md` 中补齐薄切片候选状态和处置记录。不继续开发功能；第五课将在稳定的普通业务薄片上判断一个 AI 机会。
