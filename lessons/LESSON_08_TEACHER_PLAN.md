# 第八课教师教案——Claude 执行，Codex 独立评审，主管裁决

> **核心思想：执行者可验证，独立者评审，主管批准；三者不能压成一个自动通过点。**

## 一、课程元数据与定位

| 项目 | 本课设定 |
| --- | --- |
| 学员 | 已完成第七课、掌握浏览器验收卡和证据索引的业务主管 |
| 时长 | 90 分钟硬上限：85 分钟主线 + 5 分钟机动 |
| 课堂主成果 | 独立评审 finding + 主管处置卡：包含评审上下文范围、引证证据、问题优先级，以及 accept/fix/stop/defer 决定和理由 |
| 主管判断成果 | 区分执行、验证、独立评审和批准，选择协作方式并承担最终处置理由 |
| 支撑成果 | `docs/LESSON_08_AUDIT_REPORT.md` 更新独立评审记录，只作跨课交接 |
| 数据边界 | 只使用 Mock 或已脱敏数据；不向评审者提供真实敏感数据、密钥或不必要的实现对话 |

本课用同一个个人原型串起两条学习线：原型线要求"对现有候选和证据进行一次独立评审，根据主管处置完成必要修复或明确延期"，主管线要求"区分执行、验证、独立评审和批准，选择协作方式并承担最终处置理由"。两条线分别验收，不能相互抵分。

本课不做：让 Codex 替主管批准业务；要求学员实现全部协作拓扑；向评审者提供真实敏感数据、密钥或不必要的实现对话。

开场必须先制造一个可见区别：同一个 AI 既写代码又自己说"没问题"vs 另一个不知道怎么写的 AI 只看证据独立评审后发现了问题。先让学员看见"既当运动员又当裁判员"的风险，再解释五个概念。

## 二、逆向目标、证据与核心概念

### 2.1 目标—活动—证据

| 学习目标 | 课堂活动 | 通过证据 |
| --- | --- | --- |

概念分层：核心概念为上下文隔离、独立 Finding、验证/评审/批准职责分离、独立评审、主管裁决；Agent 协作模式选型与 accept/fix/stop/defer 为操作方法；独立评审报告与主管处置卡为产物。六种协作模式名称和 Reviewer fallback 仅作背景。

### 2.2 四步概念解析公式

#### 上下文隔离

1. **是什么 / 不是什么**：评审者只接收约定的规格、候选和证据，不继承实现者的全部对话和自我辩护；不是给评审者看所有聊天记录，也不是让评审者和实现者用同一个会话。
2. **机制**：评审者拿到的是一份"隔离输入包"——契约、候选变更和证据索引，而不是开发过程中的全部对话和推演；评审者不知道实现者怎么想的，只看结果和证据。
3. **当课操作例子与边界**：Task 2 只给评审者契约、候选变更和证据索引，不传开发对话和自我辩护；材料超出约定范围时先删减。
4. **交接价值**：回指 Task 2——学员建立隔离评审输入时，只提供必要材料，不把全部开发对话也传给评审者。

#### 独立 Finding

1. **是什么 / 不是什么**：每个评审结论都要指出问题、影响、证据和建议，不是笼统说"看起来没问题"，也不是只说"这里有点问题"不说明影响。
2. **机制**：评审者对每个发现输出四项：问题是什么、对业务有什么影响、证据在哪里、建议怎么处理；finding 有优先级（高/中/低），主管按优先级处置。
3. **当课操作例子与边界**：Task 3 的每条 finding 都写清问题、业务影响、证据引证和建议，并标注优先级；没有引证的判断不能直接进入 Task 4。
4. **交接价值**：回指 Task 3—4——学员让 Codex 输出独立 findings，然后逐项决定 accept/fix/stop/defer。

#### 验证、评审与批准三分

1. **是什么 / 不是什么**：执行者可验证（自己检查行为是否正常），独立者评审（第三方看证据找问题），主管批准或拒绝；三者不能压成一个自动通过点。验证是"自己做对了吗"，评审是"别人看有没有问题"，批准是"主管决定接不接受"。
2. **机制**：Claude 执行并自验行为，Codex 独立评审找问题，主管读取 findings 后批准、打回或延期；三者由不同角色承担，不能由同一个流程自动完成。
3. **当课操作例子与边界**：Task 4—5 中，Claude 执行和自验，Codex 独立评审，主管读取 findings 后批准、打回或延期；任何一步都不能冒充另一种职责。
4. **交接价值**：回指 Task 4—5——学员区分验证、评审和批准，不让 Claude 的修复和 Codex 的评审被同一自动流程冒充为主管批准。

#### 独立评审

1. **是什么 / 不是什么**：由未参与实现的评审者在隔离上下文中检查规格、证据和变更；不是协作模式选型，也不是实现者自评或主管批准的替代品。
2. **机制**：Task 1—2 只在需要独立判断时选择评审模式；评审者接收必要输入，主管再作处置，选择最简单足够的协作方式。
3. **当课操作例子与边界**：Task 1—2 汇总评审输入并建立隔离评审时，已经实践“执行者和评审者分离”；第七课的 Subagent 调度属于另一种操作方法，不能替代本课独立评审。
4. **交接价值**：回指 Task 1—2——评审输入范围、上下文隔离和独立性要求都必须写进交接材料。

#### 主管裁决

1. **是什么 / 不是什么**：主管对 finding 作接受、修复、停止或延期决定，并记录承担理由；不是全部默认 accept，也不是让 AI 自动决定处置方式。
2. **机制**：主管逐项读取 finding，根据业务影响、风险和成本决定：accept（接受现状）、fix（修复问题）、stop（停止该功能）、defer（延期处理）；每个决定都要写理由。
3. **当课操作例子与边界**：Task 4—5 逐项读取 finding、证据和业务影响，决定 accept/fix/stop/defer 并写理由；评审者不能替主管作出决定。
4. **交接价值**：回指 Task 4—5——学员逐项决定处置方式，需要修复的由 Claude 执行，处置结果进入项目状态。

### 2.3 操作方法与扩展认识概念卡

Agent 协作模式选型与 accept/fix/stop/defer 是操作方法；独立评审报告与主管处置卡是交付产物。

#### 六种协作模式名称（认识级）

流水线、调度/执行、并行、对等、评审/辩论、人在回路仲裁是六种常见的 Agent 协作模式。全部可见，但只要求用一张对比框架识别"本课用了哪种"，不搭建六套系统。教师用 2—4 分钟展示对比框架，不逐一展开。

#### Reviewer fallback（认识级）

评审工具不可用时，可切换到隔离新会话或等价独立上下文，但不能因此跳过独立评审。例如 Codex 不可用时可以用另一个新会话只提供隔离输入来替代，关键是"独立"而非"用哪个工具"。教师用 2 分钟说明，不展开。

讲解时直接沿 Task 1—5 的真实动作讲五张核心卡：先汇总输入，再建立隔离上下文，形成 finding，区分职责，最后由主管裁决。协作模式和 accept/fix/stop/defer 作为方法嵌入 Task 4—5。总计控制在 10 分钟左右；不要逐字朗读。

## 三、教学准备与安全边界

### 课前预检

- 第七课证据可用：学员已有浏览器验收卡和 `LESSON_07_EVIDENCE_INDEX.md`。
- `docs/PROJECT_STATE.md` 有浏览器验收证据索引和上一课输入说明。
- 独立评审环境已预置：教师已配置好 Codex 评审入口或等价隔离会话方案，学员不需要自行安装。
- Working Tree 处于 Clean 状态：教师演示前先 `git status` 确认。
- 开发服务器可启动：双击 `start-project.bat` 或运行 `npm run dev`，本地预览 `http://127.0.0.1:8888/` 可访问。
- 助教理解评审工具不可用时的 fallback 方案（切换隔离新会话）。

### 实操前只讲四条红线

1. 不向评审者提供真实敏感数据、密钥或不必要的实现对话；评审者只接收约定的规格、候选和证据。
2. 不让 Codex 替主管批准业务；评审结果由主管裁决，不替代主管责任。
3. 不要求学员实现全部协作拓扑；课堂只实践"执行者和评审者分离"一种模式。
4. 不虚构 `audit_status: PASS` 或自动化审批；实际评审出什么 finding，就展示什么 finding。

教师不得虚构 Codex Auditor 独立进程、verify-project.ps1、[PASS] 全量校验等课堂能力。实际运行什么，就展示什么证据。

## 五、逐 Task 示范、口令、巡视与降级

教师统一案例只走一条路径：以工单看板为例，对 L7 的浏览器验收结果做独立评审。从汇总候选变更和证据 → 建立隔离评审输入 → Codex 输出独立 findings（如"空数据时标签不显示但未在证据索引中标记为 Bug 还是设计"）→ 主管逐项处置（accept/fix/stop/defer）→ 需要修复的由 Claude 执行后重新取证。每个 Task 均按以下四项执教。

### Task 1：汇总候选变更、契约和 L7 证据，不自评"已验收"

- **教师示范**："先把评审输入准备好。"展示如何汇总候选变更清单、L3 契约和 L7 证据索引，形成一份"评审输入包"。强调不自评"已验收"——只提供事实材料，不附自我评价。
- **教师口令**："汇总你的候选变更、L3 契约和 L7 证据索引，形成一份评审输入包。不要自评'已验收'或'没问题'，只提供事实材料。"
- **巡视判断**：评审输入包含候选、契约和证据三部分；没有自评通过或自我辩护；材料完整但不包含不必要的开发对话。
- **失败降级**：缺少契约时回到 L3 补齐；有自评内容时删除；材料过多时缩到必要范围。

### Task 2：建立隔离评审输入，只提供必要材料和范围

- **教师示范**："现在把材料交给独立评审者，但只给必要的。"展示如何把评审输入包传给 Codex（或隔离新会话），只包含契约、候选变更和证据索引，不包含开发过程中的对话和推演。
- **教师口令**：下发隔离评审提示词模板（见学员指南 Task 2）。把评审输入包传给独立评审者，只提供契约、候选变更和证据索引，不包含开发对话。
- **巡视判断**：评审者只收到约定材料；不继承实现者的全部对话和自我辩护；材料范围明确。
- **失败降级**：评审者收到太多材料时缩到必要范围；包含开发对话时删除；范围不明确时写清评审范围。

### Task 3：让 Codex 输出带引证、优先级和影响的独立 findings

- **教师示范**："让评审者独立找问题。"展示 Codex 如何输出 findings：每项有问题描述、业务影响、证据引证和建议，有优先级（高/中/低）。例如"证据索引中空数据路径标记为未证明，但没有说明是 Bug 还是设计决策——影响：IT 交接时无法判断是否需要修复；建议：明确标记并补充理由"。
- **教师口令**：下发独立评审提示词模板（见学员指南 Task 3）。让 Codex 输出独立 findings，每项有问题描述、业务影响、证据引证和建议，有优先级。
- **巡视判断**：findings 有四项（问题/影响/证据/建议）而非笼统评价；有优先级标记；引证了具体证据而非泛泛而谈。
- **失败降级**：findings 笼统时要求补充四项；缺少优先级时标记；没有引证证据时追问"证据在哪里"。

### Task 4：逐项决定 accept/fix/stop/defer，并说明业务理由

- **教师示范**："现在由主管处置。"展示如何逐项读取 finding，根据业务影响决定：高优先级"空数据路径未标记"→ fix（修复并重新取证）；中优先级"证据索引格式不统一"→ accept（接受现状，不影响业务）；低优先级"缺少边界情况测试"→ defer（延期到下一阶段）。每项写理由。
- **教师口令**：逐项决定每条 finding 的处置：accept（接受）、fix（修复）、stop（停止该功能）、defer（延期）。每项写业务理由。不要全部默认 accept。
- **巡视判断**：每项 finding 有处置决定和理由，理由至少指出业务影响和成本权衡，不是只说"问题不大"；不是全部默认 accept；fix 的有后续修复计划；stop 或 defer 有明确理由。
- **失败降级**：全部 accept 时追问"有没有需要 fix 或 defer 的"；没有理由时补写；fix 缺后续计划时补计划；理由只说"问题不大"或"可以接受"时，追问"这个 finding 影响什么业务，修复/不修复的成本各是多少"。

### Task 5：需要修复的由 Claude 执行，关键项重新取证，处置结果进入项目状态

- **教师示范**："需要修复的让 Claude 执行。"展示 Claude 如何修复"空数据路径标记"问题，修复后重新在浏览器中取证（截图显示空数据时标签状态），更新 `LESSON_08_AUDIT_REPORT.md` 和 `PROJECT_STATE.md`，记录处置结果。
- **教师口令**：对标记 fix 的 finding，让 Claude 执行修复。修复后对关键项重新取证。把处置结果写入 `LESSON_08_AUDIT_REPORT.md` 和 `PROJECT_STATE.md`。
- **巡视判断**：修复后有重新取证而非只改代码；处置结果写入审计报告和项目状态；没有把 Claude 的修复和 Codex 的评审冒充为主管批准。
- **失败降级**：修复后没有重新取证时补取证；处置结果未写入时补写；把修复冒充为批准时纠正"修复是执行，批准是主管"。

## 六、现场 Debug 与降级预案

| 问题类型 | 教师处置 | 禁止说法 |
| --- | --- | --- |
| 评审者只说"看起来没问题" | 要求输出四项 finding（问题/影响/证据/建议） | "没问题就是通过了" |
| 主管全部默认 accept | 追问"有没有需要 fix 或 defer 的" | "都接受就行了" |
| 处置理由太笼统（只说"问题不大"） | 追问"这个 finding 影响什么业务，修复成本是多少" | "接受就行了不用多想" |
| 评审工具不可用 | 切换隔离新会话或等价独立上下文 | "跳过评审直接通过" |
| 评审者收到开发对话 | 删除对话，只保留隔离输入 | "多给点信息评审更准确" |
| 把 Claude 修复冒充为主管批准 | 纠正"修复是执行，批准是主管" | "AI 改好了就是批准了" |

## 七、随堂测试、通过标准与课后任务

### 两条线分别通过

- **原型线**：对现有候选和证据进行一次独立评审，根据主管处置完成必要修复或明确延期；评审输入范围和上下文隔离方式明确。
- **主管线**：finding 有候选文件、行为证据或契约引证；主管能说明为何接受、修复、停止或延期；Claude 的修复和 Codex 的评审没有被同一自动流程冒充为主管批准。
- **LESSON_08_AUDIT_REPORT.md** 只作交接，不能抵消任何一条主线的未通过。

### 必答题（5 题）

1. 上下文隔离是什么意思？为什么评审者不能继承实现者的全部对话？
2. 独立 finding 的四项是什么？为什么"看起来没问题"不算 finding？
3. 验证、评审和批准分别由谁承担？为什么三者不能压成一个自动通过点？
4. Agent 协作模式选型的依据是什么？是不是 Agent 越多越好？
5. HITL 处置有哪四种决定？为什么不能全部默认 accept？

参考要点：评审者只接收约定材料不继承开发对话，避免自我辩护影响判断；四项是问题/影响/证据/建议，笼统评价没有可追溯信息；执行者验证/独立者评审/主管批准，三者由不同角色承担不能自动通过；根据依赖/并行性/独立性/责任选最简单足够方式，不是越多越好；accept/fix/stop/defer 四种，全部 accept 说明没有认真评审。

### 拓展题（选做，2 题）

1. 六种 Agent 协作模式分别是什么？本课实践了哪一种？为什么选这种？
2. 评审工具不可用时的 fallback 是什么？为什么不能因此跳过独立评审？
