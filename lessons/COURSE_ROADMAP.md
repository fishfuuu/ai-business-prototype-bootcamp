## 1. 课程定位与终局目标

### 核心定位与双重使命

课程目标不是培养专业的 Vue/TypeScript 程序员，而是以业务主管深度掌握与 AI Agent 协作的底层心智为基石，实现**“对外面向 IT + 对内赋能工位”的双重跃迁**：
1. **对外向 IT 控盘需求（超级业务产品经理，Super Business PM）**：借助 Coding Agent（Claude Code / Codex），用自然语言 + 模拟数据跑出可运行的原型样板间，白纸黑字冻结数据契约与业务边界，彻底终结“需求说不清、研发猜着做、上线即返工”。
2. **对内向工位日常提效（AI Agent 高阶驾驭者与部门数字化教练）**：系统掌握 Agent 交互的系统理论、分工边界与控制技巧，摆脱盲目单次聊天的玩具用法，将“护栏约束 + 工具装配 + 隔离审查 + 人在回路”完整工程心智平移至日常办公（如数据分析、制度内审、流程把关）；即使 IT 拒绝排期立项，主管也能掌握一套标准风控与交互方法论，能够自行摸索并在受控边界内探索部门日常业务的试点增效。

学员默认无代码、Git、MCP 和终端命令行基础，但熟悉本部门流程、指标、风险与决策。主管不需要去搞底层的生产服务器运维、复杂并发代码或手打 Git/Patch 命令行，而是要掌握：
1. **高保真原型控盘能力**：用自然语言 + AI 跑出可运行、可点击、带模拟数据的高保真原型系统，验证商业设想。
2. **需求与数据契约表达能力**：将口头需求标准化为《业务功能卡》、可视化数据契约卡与明确的输入/输出边界，让 IT 研发零返工。
3. **日常工作 Agentic 协作与工作流增效能力**：掌握将复杂办公任务拆解为“明确上下文 + 专用工具/Skill + 人在回路审批”的标准化交互方法，熟练运用 Agent 辅助处理海量数据、复杂比对与报告归纳。
4. **工程防护与认知防错能力**：掌握安全沙箱授权、项目级 Agent 指令与约束（`CLAUDE.md`/`AGENTS.md`）、事实锚定排错、重试预算熔断与版本恢复流程，防止 AI 幻觉扩散与项目失控。
5. **可复核证据驱动的验收与独立审查能力**：基于可复核、可重复生成的证据链完成验收；掌握“双盲独立审查（上下文隔离）”心智，引导独立 Agent 审查代码与业务文书，行使主管处置框架（accept/fix/stop/defer）一票裁决权。
6. **成熟 Agent 资产选型、评估与微调配置能力**：掌握外部 Skill 的安全体检与边界把控；能读懂企业级 SOP 技能解剖图，基于成熟标杆为本部门注入专属规则与红线阈值（拒绝从零写垃圾，追求开箱即用高质量落地）。
7. **确定性与概率性逻辑切割能力**：准确判断普通功能（确定性规则）与 AI 功能（概率性生成），坚持人在回路授权门禁（HITL）确认，在结业时输出《产品决策与开发启动包》与《部门日常 Agent 赋能落地清单》（实事求是，绝不画大饼）。

### 三层协作能力进阶框架（课程框架）

训练营帮助主管实现三层 AI 协作能力跨越：
- **第一层：Prompting (单次指令)** —— 通过单次指令描述任务，理解裸 Prompt 局限。
- **第二层：Harness Engineering (工程护栏)** —— 通过项目级 Agent 指令与约束（`CLAUDE.md`/`AGENTS.md`）、文件 (`PROJECT_STATE.md`)、Skills (`grill-me`, `diagnose`)、权限与工作流约束 Agent 执行。
- **第三层：Bounded Agent Loop (受控 Agent 循环)** —— 在明确目标、边界、工具、风险和停止条件下，让 Agent 进行受控自主循环，主管在关口依据主管处置框架行使人在回路授权门禁（HITL）盖章。

### 持久理解（Enduring Understandings）

以下五条是学员在课程结束后应内化并可迁移到真实工作中的原则，不是操作流程而是判断锚点：

1. AI 不替主管决定——从选环节到批准，判断权和责任始终在主管身上。
2. 确定性任务用规则，概率性任务才考虑 AI——最简单足够优先。
3. 没有可追溯的证据，"看起来没问题"不等于通过。
4. 执行、验证、评审和批准是四种不同角色——不能压成一个自动通过点。
5. 原型证明的是可行性，不是生产就绪——IT 接收的是决策和边界，不是上线指令。

### 教学设计与概念解析四步范式 (Pedagogical 4-Step Formula)

为避免概念浮于表面、类比失真和阅读绕路，全课程所有硬核概念（LLM, Tools, Agent, ReAct, Tokens, MCP, Git, Linters）统一采用**【四步概念解析公式】**（每课设置 3—5 个必须掌握的核心概念，并可设置 0—2 个扩展认识概念，单概念讲解控制在 3–5 分钟；四步是最小解释框架，不要求每一步都使用类比）：

> 每课设置 3—5 个必须掌握的核心概念，并可设置 0—2 个扩展认识概念。操作语言与工程背景单独记录。复合名称不得隐藏独立判断。首次核心概念使用四步概念解析公式；扩展概念不设独立通过门槛。
1. **工程定义 (Engineering Definition)**：使用必要且准确的 IT/软件工程术语，讲清工程本质，明确“是什么”与“不是什么”。
2. **运作机制 (Underlying Mechanism)**：解释代码、接口、数据或协作步骤实际如何流转；能用当课操作直接说明时，不额外引入抽象场景。
3. **当课操作例子与边界 (Task Example & Boundary)**：优先回指学员刚完成的真实 Task，说明它在什么条件下成立、何时不成立。只有直说仍不够清楚时，才补一套简短、稳定的业务类比与反例；类比不是必选项，不能引入新的术语或第二套映射。
4. **IT 沟通与交接价值 (Handoff Value)**：明确该概念对应学员**刚完成的哪一步实操**，以及主管为何需要用该词与 IT 沟通或作出判断。

### 可选反思追问（Optional Reflection Prompts）

以下反思问题不是固定环节。教师仅在概念核对阶段时间有余裕时使用，且只针对当前课与前课有直接概念迁移关系时。不要做成每课必问的结构性环节。

- **L5（迁移自 L4）**：你在 L4 做的薄切片要求"小到能独立验证"。这个原则怎么帮你判断哪个环节适合先加 AI？
- **L7（迁移自 L6）**：你在 L6 学的"事实-假设-编造"区分，怎么帮你判断证据链是否充分？
- **L9（迁移自 L8）**：你在 L8 学的 accept/fix/stop/defer 处置框架，怎么帮你决定哪个环节不做 AI？

只有这三个课对有最直接的跨课概念迁移，其余课的跨课桥接语句已经足够。

### 训练营支持的四类业务原型与 Mock 机制

训练营全课程持续贯穿支持四类典型业务原型，学员从 L1 起持续发展自己的部门原型：
1. **A. 监控与决策型**：适合经营分析、异常监控、投产分析、履约预警（看指标 -> 看异常 -> 下钻明细 -> 做出决策）。
2. **B. 任务与流程型**：适合预算申请、退货处理、工单派发、单据审批（创建记录 -> 处理任务 -> 状态流转 -> 推进下一步）。
3. **C. 操作工具型**：适合文案生成、规则计算、数据整理、格式转换（输入 -> 规则处理 -> 结果输出 -> 人工确认/复制/导出）。
4. **D. 研发创作工作台型 (R&D & Creative Studio)**：适合品牌设计、服装研发、视觉企划、工业打样等非线性、多模态、重资产流转部门（素材/企划输入 ➔ 风格与规格硬规则约束 ➔ 多模态生成与局部调优 ➔ 方案横向比对与合规检查 ➔ 导出交付资产包 Tech Pack）。

**所有原型的双重交付终局（Universal Dual Delivery Model）**：
无论是 A 监控、B 流程、C 工具还是 D 研发创作台，原型均具备双重价值终局：
1. **IT 立项开发包 (IT Starter Pack)**：白纸黑字沉淀数据契约、业务状态机与生产差距，交接 IT 研发团队排期上线；
2. **工位自用单机工具 (Standalone Desk Utility)**：脱离企业复杂 IT 服务器排期依赖，直接在学员本地（127.0.0.1）持久化运行，作为个人与科室日常业务中开箱即用的生产力辅助台，杜绝“IT 不排期则原型作废”。

**工位单机自治运行形态强制红线与数据桥接规约**：
单机自用形态绝不等于生产系统上线，必须严格遵守四条刚性边界：
1. **非生产声明不降级**：本地单机运行仅作为个人/科室日常办公辅助决策工具，严禁对外开放公网访问或跨局域网多用户并发部署；
2. **本地脱敏输入**：严禁在单机工具中明文录入未脱敏的机密商业数据、敏感客户个人信息（PII）或生产系统核心密钥；
3. **人在回路（HITL）逐笔确权**：单机工具中任何分析、建议或导出动作，必须由主管人工逐笔核验确认后方可采用，严禁赋予其免审自动闭环权限；
4. **严禁越过 IT 接入内部生产接口**：单机工具严禁擅自私接未经 IT 部门审核授权的内部生产数据库或写操作 API；生产级系统开发与推广必须以《产品决策与开发启动包》移交 IT 团队排期实施。

**教师演示与学员原型边界**：
- 教师十课统一演示案例：“业务异常预警与闭环处置工作台”。
- 学员从 L1 开始持续发展自己部门的业务原型。
- 普通学员默认使用 Mock 数据；教师在受控环境下演示真实模型/API调用。学员无需配置 API Key 或 MCP。
- **Mock 职责分工**：
  1. **主管**：定义字段、含义、枚举、范围和流程规则，并验证业务合理性。
  2. **课程团队**：提供模板与安全规则。
  3. **Agent**：起草明确标记的合成数据。
  4. **教师/助教**：检查确认无真实敏感数据。

### 每课共同结构

- **双轨两线最低证据独立性（P-04 规约）**：原型推进线（代码沙盘）与主管判断线（管理实战）分别设置最低证据，独立核验，**严禁相互折抵**。
- 每课提供一张整课融合心智模型；课堂节奏表只给教师。
- 教师教案 8 模块；学员指南 6 大章；一课一份指南，分支嵌入同一指南。
- 常见误区最多 5 项；问题处理最多 5 类。

## 2.5 主管判断线进阶带 Rubric

> **设计说明**：本 Rubric 描述学员在每个阶段**做什么**（可观察行为），而非"理解什么"。每个 Band 的行为来自各课教案中冻结的"主管判断成果"。Rubric 供教师和 AI 辅导系统共同使用：教师据此判断学员所处的 Band 并决定是否放行；AI 辅导系统据此推送 Band 级别的反思问题、识别跃迁信号语言、给出对齐反馈。AI 不做最终 Band 判定——判断力发展是情境相关且非线性的，最终 Band 由教师确认。
>
> **使用边界**：Rubric 是辅助工具，不是自动评分器。学员不需要逐 Band 线性爬升——某人可能 L1 就说出 Competent 级别的判断，也可能 L8 才真正稳定 Emerging 行为。教师按学员当前课堂表现对号入座，不按课次机械对应。

### Band 定义

| Band | 覆盖课次 | 学员能做什么（可观察行为） | 跃迁信号（语言/行为标记） |
| --- | --- | --- | --- |
| **Emerging（萌芽）** | L1 | 能区分 LLM、Tools、Agent 三个概念，并用自己的话说出主管在定义、范围和验收中各自的责任。 | 学员开始说"这个是 Agent 做的"而非"AI 帮我做的"；能指出"这一步需要我确认"而非默认 Agent 全自动。 |
| **Developing（发展）** | L2–L3 | L2：能说明每一条 Keep/Omit/Modify 裁决的业务理由，能指出判断如何落在页面上。L3：能回答"谁遇到什么问题、为什么要做、目标是什么、边界在哪里、错了有什么风险、怎样算通过、何时必须停"七问。 | 学员从"我觉得这样好看"转向"这条约束服务于XX业务目标"；从"需求大概是这样"转向"边界在这里，超出边界不做"。 |
| **Competent-Emerging（胜任初阶）** | L4 | 能裁定切片是否足够小又足够完整，能区分业务状态与技术状态，并在实施前后分别确权。 | 学员从"先做完再说"转向"这个切片能独立验证吗"；从"页面变了就是成了"转向"技术状态变了但业务状态还没确权"。 |

## 3. 工具分工与角色契约

### 1. Claude Code（主要实施者 / 开发 Agent）
- 需求解构与方案推演
- 页面与组件增量创建
- 执行 **ReAct 范式**、**Plan & Execute 范式** 与 **Subagent 调度**

### 2. Codex（独立审查者 / 审计 Agent）
- 从第 8 课开始正式引入（基于独立审查上下文隔离规则）
- **独立审查上下文隔离**：新建只读独立会话，仅调取已确认需求、稳定 Commit 与 Candidate Commit 的版本变更
- 审查隐患、逻辑越界与未授权的范围修改，只读不修改代码
- 提供自然语言审计意见（阻断/重要/建议）

### 3. 主管（最终裁决者 / 人在回路授权门禁盖章官）
- 掌控 Workflow 推进阶段
- 行使 Keep / Omit / Remove / Modify 裁决权
- 对 Codex 审查意见做出 4 种决定：accept（接受）、fix（修复）、stop（停止）、defer（延期）
- **依据主管处置框架（accept/fix/stop/defer）**签署人在回路授权门禁（HITL）授权，完成最终业务验收

## 4. 高阶工程防错 8 大防护规则 (Robustness & Patch Rules)

为防止教学实操中出现卡死、白屏、死循环和弹窗风暴，全课程严格注入 8 大高阶防错机制：

1. **Subagent 超时熔断规则 (Subagent Lifecycle & Timeout Rule)**（L7 引入并讲解）：
   派发给子智能体（如静默测试 Subagent）的独立任务必须明确设置超时与停止条件（如 `DurationSeconds: 60`），超时自动释放，决不挂起主 Agent。
2. **Subagent 预授权与只读沙箱规则 (Subagent Read-only Sandbox Rule)**（L7 引入并讲解）：
   静默后台运行的 Subagent 仅继承只读工具权限 (Read-only Tools)，写权限修改动作必须返回主 Agent 界面由主管签署 HITL 口令确认。
3. **Subagent 产物强制磁盘落盘规则 (Disk Persistence Rule)**（L7 引入并讲解）：
   Subagent 产出的所有测试截图、DOM 操作日志与检查报告，必须写入本地磁盘目录（`local-backups/`）与 `PROJECT_STATE.md`，决不随 Context 重置而蒸发。
4. **双 Agent 两轮仲裁门禁 (2-Round HITL Arbitration Rule)**：
   第 8 课开发 Agent 与只读审查 Agent 辩论超过 2 轮时，强制阻断自动循环，引发主管仲裁盖章。
5. **Fallback 来源与失败责任 (Mock Fallback Bridge)**：
   第 9~10 课真 AI 接口连接失败、网络超时或非法返回时，降低调用失败导致页面不可用的风险，显示降级来源并降级回 Mock Data 结构化渲染。
6. **有界排错与重试预算/熔断 (Bounded Debugging & Retry Budget)**：
   第 6 课排错严格限定在"界面呈现与业务契约不一致"的领域，严禁主管手打 Git/Patch 命令或深挖底层代码；同一 Bug 最多由 Agent 自修 2 轮，超过两轮后停止自动修改，保留诊断证据，并由教师或助教恢复到已确认基线。
7. **独立上下文审查与主管处置框架 (Context-Isolated Audit & Supervisor Adjudication)**：
   第 8 课 Codex 必须在全新的只读独立会话中开启，只读取 Candidate Commit 的版本变更；若双 Agent 辩论满 2 轮未达成一致，主管依据主管处置框架（accept/fix/stop/defer）行使一票裁决权。
8. **确定性/概率性切割与自动化边界 (Deterministic vs. Probabilistic Cut & Automation Boundary)**：
   计算与状态流转由确定性代码执行；智能生成由 LLM 执行且须经过人在回路授权门禁（HITL）确认；不可逆、高敏感、责任不清和难验证的事项默认不进入自主执行。

### 第 2 课：让原型变得清楚、可信、能用
* **定位**：根据业务目的选择信息结构与参考图，完成视觉重构，掌握项目级 Agent 约束 / Agent Harness、约束作用域与优先级、行为约束与设计约束、信息优先级与视觉层级和约束一致性验证；多模态提取、设计映射、Keep/Omit/Modify 与视觉证据对比为操作方法；保留版本证据，不要求两个 Commit。
* **主要内容**：
  1. **Task 1：结构提取 (15 分钟)**：多模态提取参考图首屏布局与视觉主次，按设计规则忽略与目标界面无关的视觉元素。

* **双线最低证据 (P-04)**：代码与工具沙盘线（导出的《IT 系统开发启动包》或《工位自用单机工具包》完整目录与生产/落地差距清单）；主管判断线（全员提交的汇报讲稿/PPT + 签署的《部门日常 Agent 赋能落地清单》+ 3–5人现场答辩记录）。互不抵扣。
