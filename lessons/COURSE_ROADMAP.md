## 1. 课程定位与终局目标

### 核心定位

课程目标不是培养专业的 Vue/TypeScript 程序员，而是借助 Coding Agent（Claude Code / Codex），将各部门业务主管培养为“超级业务产品经理（Super Business PM）”。

学员默认无代码、Git、MCP 和终端命令行基础，但熟悉本部门流程、指标、风险与决策。主管不需要去搞底层的生产服务器运维、复杂并发代码或手打 Git/Patch 命令行，而是要掌握：
1. **高保真原型控盘能力**：在 2 小时内用自然语言 + AI 跑出可运行、可点击、带模拟数据的高保真原型系统。
2. **需求与数据契约表达能力**：将口头需求标准化为《业务功能卡》、可视化数据契约卡与明确的输入/输出边界。
3. **工程防护与版本证据管理能力**：掌握安全沙箱授权、项目级 Agent 指令与约束（`CLAUDE.md`/`AGENTS.md`）、事实锚定排错与版本恢复流程，防止项目失控。
4. **可复核证据驱动的验收与审查能力**：基于可复核、可重复生成的证据链完成验收，并在独立审查上下文隔离下依据主管处置框架（accept/fix/stop/defer）引导 Codex 进行代码审查与一票裁决。
5. **确定性与概率性逻辑切割能力**：准确判断普通功能（确定性规则）与 AI 功能（概率性生成），坚持人在回路授权门禁（HITL）确认，在结业时输出《产品决策与开发启动包》（明确声明非生产就绪系统，供 IT 开始正式设计与开发，而非直接上线）。

### 三层协作能力进阶框架（课程框架）

训练营帮助主管实现三层 AI 协作能力跨越：
- **第一层：Prompting (单次指令)** —— 通过单次指令描述任务，理解裸 Prompt 局限。
- **第二层：Harness Engineering (工程护栏)** —— 通过项目级 Agent 指令与约束（`CLAUDE.md`/`AGENTS.md`）、文件 (`PROJECT_STATE.md`)、Skills (`grill-me`, `diagnose`)、权限与工作流约束 Agent 执行。
- **第三层：Bounded Agent Loop (受控 Agent 循环)** —— 在明确目标、边界、工具、风险和停止条件下，让 Agent 进行受控自主循环，主管在关口依据主管处置框架行使人在回路授权门禁（HITL）盖章。

### 持久理解（Enduring Understandings）

以下五条是学员在课程结束后应内化并可迁移到真实工作中的原则，不是操作流程而是判断锚点：

1. AI 不替主管决定——从选环节到批准，判断权和责任始终在主管身上。
2. 确定性任务用规则，概率性任务才考虑 AI——最简单足够优先。
3. 没有可追溯的证据，"看起来没问题"不等于通过。
4. 执行、验证、评审和批准是四种不同角色——不能压成一个自动通过点。
5. 原型证明的是可行性，不是生产就绪——IT 接收的是决策和边界，不是上线指令。

### 教学设计与概念解析四步范式 (Pedagogical 4-Step Formula)

为避免概念浮于表面、类比失真和阅读绕路，全课程所有硬核概念（LLM, Tools, Agent, ReAct, Tokens, MCP, Git, Linters）统一采用**【四步概念解析公式】**（每课设置 3—5 个必须掌握的核心概念，并可设置 0—2 个扩展认识概念，单概念讲解控制在 3–5 分钟；四步是最小解释框架，不要求每一步都使用类比）：

> 每课设置 3—5 个必须掌握的核心概念，并可设置 0—2 个扩展认识概念。操作语言与工程背景单独记录。复合名称不得隐藏独立判断。首次核心概念使用四步概念解析公式；扩展概念不设独立通过门槛。
1. **工程定义 (Engineering Definition)**：使用必要且准确的 IT/软件工程术语，讲清工程本质，明确“是什么”与“不是什么”。
2. **运作机制 (Underlying Mechanism)**：解释代码、接口、数据或协作步骤实际如何流转；能用当课操作直接说明时，不额外引入抽象场景。
3. **当课操作例子与边界 (Task Example & Boundary)**：优先回指学员刚完成的真实 Task，说明它在什么条件下成立、何时不成立。只有直说仍不够清楚时，才补一套简短、稳定的业务类比与反例；类比不是必选项，不能引入新的术语或第二套映射。
4. **IT 沟通与交接价值 (Handoff Value)**：明确该概念对应学员**刚完成的哪一步实操**，以及主管为何需要用该词与 IT 沟通或作出判断。

### 可选反思追问（Optional Reflection Prompts）

以下反思问题不是固定环节。教师仅在概念核对阶段时间有余裕时使用，且只针对当前课与前课有直接概念迁移关系时。不要做成每课必问的结构性环节。

- **L5（迁移自 L4）**：你在 L4 做的薄切片要求"小到能独立验证"。这个原则怎么帮你判断哪个环节适合先加 AI？
- **L7（迁移自 L6）**：你在 L6 学的"事实-假设-编造"区分，怎么帮你判断证据链是否充分？
- **L9（迁移自 L8）**：你在 L8 学的 accept/fix/stop/defer 处置框架，怎么帮你决定哪个环节不做 AI？

只有这三个课对有最直接的跨课概念迁移，其余课的跨课桥接语句已经足够。

### 训练营支持的三类业务原型与 Mock 机制

训练营全课程持续贯穿支持三类典型业务原型，学员从 L1 起持续发展自己的部门原型：
1. **A. 监控与决策型**：适合经营分析、异常监控、投产分析、履约预警（看指标 -> 看异常 -> 下钻明细 -> 做出决策）。
2. **B. 任务与流程型**：适合预算申请、退货处理、工单派发、单据审批（创建记录 -> 处理任务 -> 状态流转 -> 推进下一步）。
3. **C. 操作工具型**：适合文案生成、规则计算、数据整理、格式转换（输入 -> 规则处理 -> 结果输出 -> 人工确认/复制/导出）。

**教师演示与学员原型边界**：
- 教师十课统一演示案例：“业务异常预警与闭环处置工作台”。
- 学员从 L1 开始持续发展自己部门的业务原型。
- 普通学员默认使用 Mock 数据；教师在受控环境下演示真实模型/API调用。学员无需配置 API Key 或 MCP。
- **Mock 职责分工**：
  1. **主管**：定义字段、含义、枚举、范围和流程规则，并验证业务合理性。
  2. **课程团队**：提供模板与安全规则。
  3. **Agent**：起草明确标记的合成数据。
  4. **教师/助教**：检查确认无真实敏感数据。

### 每课共同结构

- 原型推进线与主管判断线分别设置最低证据，不能相互抵分。
- 每课提供一张整课融合心智模型；课堂节奏表只给教师。
- 教师教案 8 模块；学员指南 6 大章；一课一份指南，分支嵌入同一指南。
- 常见误区最多 5 项；问题处理最多 5 类。

## 2.5 主管判断线进阶带 Rubric

> **设计说明**：本 Rubric 描述学员在每个阶段**做什么**（可观察行为），而非"理解什么"。每个 Band 的行为来自各课教案中冻结的"主管判断成果"。Rubric 供教师和 AI 辅导系统共同使用：教师据此判断学员所处的 Band 并决定是否放行；AI 辅导系统据此推送 Band 级别的反思问题、识别跃迁信号语言、给出对齐反馈。AI 不做最终 Band 判定——判断力发展是情境相关且非线性的，最终 Band 由教师确认。
>
> **使用边界**：Rubric 是辅助工具，不是自动评分器。学员不需要逐 Band 线性爬升——某人可能 L1 就说出 Competent 级别的判断，也可能 L8 才真正稳定 Emerging 行为。教师按学员当前课堂表现对号入座，不按课次机械对应。

### Band 定义

| Band | 覆盖课次 | 学员能做什么（可观察行为） | 跃迁信号（语言/行为标记） |
| --- | --- | --- | --- |
| **Emerging（萌芽）** | L1 | 能区分 LLM、Tools、Agent 三个概念，并用自己的话说出主管在定义、范围和验收中各自的责任。 | 学员开始说"这个是 Agent 做的"而非"AI 帮我做的"；能指出"这一步需要我确认"而非默认 Agent 全自动。 |
| **Developing（发展）** | L2–L3 | L2：能说明每一条 Keep/Omit/Modify 裁决的业务理由，能指出判断如何落在页面上。L3：能回答"谁遇到什么问题、为什么要做、目标是什么、边界在哪里、错了有什么风险、怎样算通过、何时必须停"七问。 | 学员从"我觉得这样好看"转向"这条约束服务于XX业务目标"；从"需求大概是这样"转向"边界在这里，超出边界不做"。 |
| **Competent-Emerging（胜任初阶）** | L4 | 能裁定切片是否足够小又足够完整，能区分业务状态与技术状态，并在实施前后分别确权。 | 学员从"先做完再说"转向"这个切片能独立验证吗"；从"页面变了就是成了"转向"技术状态变了但业务状态还没确权"。 |
| **Competent（胜任）** | L5–L7 | L5：能解释为什么所选环节不能只用确定性规则，或反过来为什么应拒绝 Agent，范式与任务性质匹配。能写下拒绝理由（基于任务性质和错误代价），而非仅口头表达。L6：能区分事实、假设和模型编造，决定继续、重试、停止、升级或恢复。L7：能把验收场景、自动操作、可见观察、原始证据和结论串起来，并知道自动化证据不能替代业务批准。 | L5：从"加个 AI 试试"转向"这个环节不需要 AI，用规则更可靠"。L6：从"Agent 说修好了"转向"事实报告显示什么，我的假设是什么，还差什么证据"。L7：从"测试通过了"转向"工具验证了什么，我验收了什么，这两件事不一样"。 |
| **Competent-Extending（胜任延伸）** | L8 | 能区分执行、验证、独立评审和批准四个不同角色，能选择协作方式并承担最终处置理由（accept/fix/stop/defer），而非全部默认 accept。理由指向业务影响和成本权衡，不是笼统的"问题不大"。 | 学员从"代码写完了就通过了"转向"执行者验证不等于独立评审通过，独立评审通过不等于我批准"；能说出"这项 defer 是因为XX风险暂时可控"。 |
| **Extending（延伸）** | L9–L10 | L9：能形成部门 AI 机会地图，能够拒绝不需要 AI 或不应自动化的环节，并为值得验证的环节选择范式。拒绝理由引用本部门具体业务约束，而非泛化套用。L10：能作出继续、调整、暂缓或停止的产品决定，明确生产化前置和责任人，知道原型不等于生产就绪。 | L9：从"哪里能用 AI"转向"哪里不该用 AI，理由是什么"。L10：从"原型跑通了可以上线"转向"这些环节已证实，这些仍不能上线，IT 下一步做什么"。 |

### AI 辅导系统使用方式

| 功能 | AI 能做 | AI 不能做 |
| --- | --- | --- |
| 反思问题推送 | 按 Band 推送对应级别的反思问题（如 Developing 级推"你的 Keep/Omit 决策各自服务哪个业务目标？"） | 不替代教师决定学员是否进入下一 Band |
| 跃迁信号识别 | 识别学员语言中的 Band 跃迁信号词汇，提示"你刚才的表述接近 Competent 级别" | 不自动升级 Band——信号出现不等于稳定胜任 |
| 词汇对齐反馈 | 检查学员用词是否与本课 Glossary 词条对齐，指出口语化表达和对应专业术语 | 不因用词不规范直接判定 Band 不合格 |
| 证据对照 | 把学员口述的判断理由与教案中"主管判断成果"逐项对照，标记已覆盖和遗漏项 | 不替学员补充理由——只标记缺口，由学员自行补全 |

### 教师使用方式

1. **课中快速定位**：每课 Task 结束后，教师对照本课对应 Band 的"可观察行为"列，判断学员当前行为落在哪个 Band。
2. **不放行条件**：如果学员的行为停留在 Emerging 而本课要求 Competent-Emerging，教师需在课堂内追加一次口头追问（追问内容参照"跃迁信号"列），再决定是否放行。
3. **跨课追踪**：教师可在 `docs/PROJECT_STATE.md` 中记录学员当前 Band 和跃迁信号出现课次，供后续课程参考。
4. **Rubric 不是扣分工具**：Band 低不等于课程不及格——它帮助教师决定在哪里多花时间，而非惩罚学员。

## 3. 工具分工与角色契约

### 1. Claude Code（主要实施者 / 开发 Agent）
- 需求解构与方案推演
- 页面与组件增量创建
- 执行 **ReAct 范式**、**Plan & Execute 范式** 与 **Subagent 调度**
- 本地调试与自测验证（学员：本课规定的验证方式）

### 2. Codex（独立审查者 / 审计 Agent）
- 从第 8 课开始正式引入（基于独立审查上下文隔离规则）
- **独立审查上下文隔离**：新建只读独立会话，仅调取已确认需求、稳定 Commit 与 Candidate Commit 的版本变更
- 审查隐患、逻辑越界与未授权的范围修改，只读不修改代码
- 提供自然语言审计意见（阻断/重要/建议）

### 3. 主管（最终裁决者 / 人在回路授权门禁盖章官）
- 掌控 Workflow 推进阶段
- 行使 Keep / Omit / Remove / Modify 裁决权
- 对 Codex 审查意见做出 4 种决定：accept（接受）、fix（修复）、stop（停止）、defer（延期）
- **依据主管处置框架（accept/fix/stop/defer）**签署人在回路授权门禁（HITL）授权，完成最终业务验收

## 4. 高阶工程防错 8 大防护规则 (Robustness & Patch Rules)

为防止教学实操中出现卡死、白屏、死循环和弹窗风暴，全课程严格注入 8 大高阶防错机制：

1. **Subagent 超时熔断规则 (Subagent Lifecycle & Timeout Rule)**（L7 引入并讲解）：
   派发给子智能体（如静默测试 Subagent）的独立任务必须明确设置超时与停止条件（如 `DurationSeconds: 60`），超时自动释放，决不挂起主 Agent。
2. **Subagent 预授权与只读沙箱规则 (Subagent Read-only Sandbox Rule)**（L7 引入并讲解）：
   静默后台运行的 Subagent 仅继承只读工具权限 (Read-only Tools)，写权限修改动作必须返回主 Agent 界面由主管签署 HITL 口令确认。
3. **Subagent 产物强制磁盘落盘规则 (Disk Persistence Rule)**（L7 引入并讲解）：
   Subagent 产出的所有测试截图、DOM 操作日志与检查报告，必须写入本地磁盘目录（`local-backups/`）与 `PROJECT_STATE.md`，决不随 Context 重置而蒸发。
4. **双 Agent 两轮仲裁门禁 (2-Round HITL Arbitration Rule)**：
   第 8 课开发 Agent 与只读审查 Agent 辩论超过 2 轮时，强制阻断自动循环，引发主管仲裁盖章。
5. **Fallback 来源与失败责任 (Mock Fallback Bridge)**：
   第 9~10 课真 AI 接口连接失败、网络超时或非法返回时，降低调用失败导致页面不可用的风险，显示降级来源并降级回 Mock Data 结构化渲染。
6. **有界排错与重试预算/熔断 (Bounded Debugging & Retry Budget)**：
   第 6 课排错严格限定在"界面呈现与业务契约不一致"的领域，严禁主管手打 Git/Patch 命令或深挖底层代码；同一 Bug 最多由 Agent 自修 2 轮，超过两轮后停止自动修改，保留诊断证据，并由教师或助教恢复到已确认基线。
7. **独立上下文审查与主管处置框架 (Context-Isolated Audit & Supervisor Adjudication)**：
   第 8 课 Codex 必须在全新的只读独立会话中开启，只读取 Candidate Commit 的版本变更；若双 Agent 辩论满 2 轮未达成一致，主管依据主管处置框架（accept/fix/stop/defer）行使一票裁决权。
8. **确定性/概率性切割与自动化边界 (Deterministic vs. Probabilistic Cut & Automation Boundary)**：
   计算与状态流转由确定性代码执行；智能生成由 LLM 执行且须经过人在回路授权门禁（HITL）确认；不可逆、高敏感、责任不清和难验证的事项默认不进入自主执行。

## 6. 每课详细路线

### 第 1 课：从业务问题创建第一个系统页面
* **定位**：零基础学员建立三类业务原型分类认知、AI Agent 人机协作认知、受控 Agent 原型体验、Tools 权限沙箱与模拟数据安全红线。
* **主要内容**：
  1. 工具预检与沙箱授权：确认工程环境正常，用四步概念解析公式解析大语言模型（LLM）、AI Agent、工具接口（Tools）与业务原型四个核心概念；ReAct 只作扩展认识；Workflow、HITL、Context、项目级 Agent 指令与约束仅作教师背景。

  4. 遵照模拟数据红线，以“模型提出下一步—工具执行—主管确认”的 plain-language 体验完成首个包含侧栏菜单与 Mock 数据信息的系统雏形。

### 第 5 课：第一次把 AI/Agent 融入业务
* **定位**：第一次正式教授并实践"AI/Agent 如何融入业务"。主管只选一个低风险、可验证的智能环节，在原型中模拟正常和至少一种不确定/失败结果。核心概念为 AI 介入层级、确定性任务与概率性任务、Workflow 与 Agent、ReAct、人在回路授权门禁（HITL）；扩展认识为增量实施范式（Plan & Execute）迁移比较、护栏（Guardrail）。
* **主要内容**：
  1. **拆解业务薄片**：按三类原型（监控决策型/任务流程型/操作工具型）将第四课薄切片拆成覆盖业务决策闭环的逐个动作，标注每个动作的当前执行方式，严禁只拆纯 UI/算数步骤。

  3. **选候选与范式**：选一个低风险候选环节，选择 Workflow、ReAct 或增量实施范式（Plan & Execute），填写智能机会卡（数据、工具、HITL 检查点、停止条件、降级条件）。

### 第 6 课：用事实找 Bug，在边界内修复
* **定位**：用事实锚定排错与五层诊断方法，在边界内定位问题。核心概念为事实/假设/生成错误、根因与表象、有界排错、重试预算/熔断、停止/升级/恢复；`$diagnose` Skill 在 Task 1 激活后全程运行，主管在每个 Phase 边界只做判断和授权。

### 第 7 课：让 Agent 操作页面并留下验收证据
* **定位**：工具验证行为，主管验收业务；测试通过不等于业务正确或可以上线。通过教师预配置的**单一浏览器验收入口**驱动 Agent 操作页面并保存可追溯证据。核心概念为 MCP 最小模型、Subagent、自动化验证与业务验收、证据链、不可信输入与提示注入；浏览器验收、场景迁移和 Subagent 安全规程为方法。
* **主要内容**：
  1. **Task 1 验收场景迁移**：从 L3/L4 选择一个验收场景，明确正常与失败/降级预期，把给定条件、动作和可见结果翻译成浏览器可执行步骤。
  2. **Task 2 浏览器自动验收**：由主管在预配置单一入口发起 Agent 浏览器验收，操作页面并保存截图和日志；工具失败时明确报告，不换成代码推测。

  4. **Task 4 失败路径补证**：对一个失败/降级路径补证，形成 `docs/LESSON_07_EVIDENCE_INDEX.md` 证据索引（场景→操作→观察→原始证据→结论）。

### 第 8 课：Claude 执行，Codex 独立评审，主管裁决
* **定位**：执行者可验证，独立者评审，主管批准；三者不能压成一个自动通过点。新建隔离会话审计候选变更，主管依据证据裁决。核心概念为上下文隔离、独立 Finding、验证/评审/批准职责分离、独立评审、主管裁决；协作模式选型与 accept/fix/stop/defer 为方法。
* **主要内容**：
  1. **Task 1 汇总评审输入**：汇总候选变更、契约和 L7 证据，不自评"已验收"。
  2. **Task 2 隔离评审**：建立隔离评审输入，只提供必要材料和范围，不继承实现者的全部对话和自我辩护。
  3. **Task 3 独立评审**：让 Codex 输出带引证、优先级和影响的独立 findings（问题、影响、证据、建议），不是笼统说"看起来没问题"。
  4. **Task 4 主管处置**：逐项决定 accept/fix/stop/defer，并说明业务理由，不是全部默认 accept。
  5. **Task 5 修复与归档**：需要修复的由 Claude 执行，关键项重新取证，处置结果更新到 `docs/PROJECT_STATE.md`。
* **执行文档**：[LESSON_08_GUIDE.md](LESSON_08_GUIDE.md) 与 [LESSON_08_TEACHER_PLAN.md](LESSON_08_TEACHER_PLAN.md)。

### 第 9 课：画出部门 AI 机会与 Agent 范式选型图
* **定位**：不是"我的部门能不能用 Agent"，而是逐环节判断任务性质、可验证性、风险和合适范式。从 L5 的"一个候选点"扩展为流程级主管判断。核心概念为 AI 机会、AI 介入层级、Agent 范式、三链区分、Fallback 来源与失败责任；机会地图、介入迁移和范式选型为方法。
* **主要内容**：
  1. **Task 1 流程拆解**：画出部门一条真实业务流程，拆成具体人工/系统动作，每个有输入和输出。
  2. **Task 2 逐环节评估**：对每个动作记录输入、判断性质（确定性/概率性）、可验证性、错误代价和数据风险，不只标"适合 AI"。
  3. **Task 3 层级选择**：选择 AI 介入层级，明确拒绝 AI/Agent 的环节及理由，至少有一个"不使用 AI/Agent"的有理由决定。
  4. **Task 4 范式选型**：对保留候选选择范式（Workflow、ReAct、增量实施范式（Plan & Execute）等），补数据、工具、HITL 和停止条件。
  5. **Task 5 三链与决策**：画三链责任与 fallback（开发工具链、产品业务 API 链、模型 API 链），选出一个优先候选和一个明确不做项；降级结果不能伪装成真实成功。
* **执行文档**：[LESSON_09_GUIDE.md](LESSON_09_GUIDE.md) 与 [LESSON_09_TEACHER_PLAN.md](LESSON_09_TEACHER_PLAN.md)。

### 第 10 课：冻结原型包，形成产品决策与开发启动包
* **定位**：收口十课主线，不再新增功能；把原型、契约、智能机会、证据、评审、红线、责任和未完成项交给 IT，明确哪些仍不能上线。核心概念为原型与生产系统、风险红线与非目标、产品决策、生产就绪缺口、责任交接；就绪度检查为方法，开发启动包为产物。
* **主要内容**：
  1. **Task 1 资产盘点**：盘点十课资产，区分已证实、仅 Mock/模拟、未验证和明确未实现四类，每项有来源和状态标签。
  2. **Task 2 红线与选型确认**：对照 L9 选型，确认保留的智能机会、拒绝项、风险红线与 owner，每项有理由。
  3. **Task 3 证据覆盖范围**：用 L7/L8 证据说明原型在哪些范围内成立，列出未解决 findings。
  4. **Task 4 产品决策**：作出继续/调整/暂缓/停止的产品决定，并形成 IT 下一步清单（有优先级和前置）。
  5. **Task 5 五分钟汇报**：完成五分钟汇报——业务问题、原型证据、AI 选择、风险边界、需要 IT 做什么。
* **执行文档**：[LESSON_10_GUIDE.md](LESSON_10_GUIDE.md) 与 [LESSON_10_TEACHER_PLAN.md](LESSON_10_TEACHER_PLAN.md)。
