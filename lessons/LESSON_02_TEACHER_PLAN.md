# 第二课教师教案——让原型变得清楚、可信、能用

> **核心思想：让主管把"我觉得不好看"转成可说明、可执行、可比较的业务视觉判断。**

## 一、课程元数据与定位

| 项目 | 本课设定 |
| --- | --- |
| 学员 | 已完成第一课、掌握基础五位一体架构与本地预览加载的业务主管 |
| 时长 | 90 分钟硬上限：85 分钟主线 + 5 分钟机动 |
| 课堂主成果 | 视觉重构版个人原型：包含前后对照、3—5 条设计约束及其页面落点，以及主管的 Keep/Omit/Modify 裁决 |
| 主管判断成果 | 能说明保留、舍弃和修改的业务理由，能指出判断如何落在页面上 |
| 支撑成果 | `docs/PROJECT_STATE.md` 更新设计约束与裁决记录，只作跨课交接 |
| 数据边界 | 只使用 Mock 或已脱敏数据；不输入真实密钥、账号和业务接口 |
| 正式业务 AI 起点 | L5；L2 的 Agent 是帮助改造原型的开发执行者，不判断业务是否适合 AI |

本课用同一个个人原型串起两条学习线：原型线要求"在不增加业务功能的前提下改善信息层级、布局、状态表达和操作清晰度"，主管线要求"从参考图提取意图，决定 Keep/Omit/Modify 并指出判断如何落在页面上"。两条线分别验收，不能相互抵分。

本课不做：扩大业务范围、新增第二条主路径、把 Token/CSS/Git 变成主管主要学习任务、照搬参考图中的业务字段和数据、判断业务 AI 机会。不要求主管手写 CLAUDE.md/AGENTS.md 内容；用 /init 生成后只做核对和补充。

开场必须先制造一个可见区别：第一课的粗糙原型 vs 参考图引导的视觉重构版。先让学员看见"视觉重构不是重新做，而是让现有原型更清楚"，再解释五个概念。

## 二、逆向目标、证据与核心概念

### 2.1 目标—活动—证据

| 学习目标 | 课堂活动 | 通过证据 |
| --- | --- | --- |
| 学员能从参考图提取布局、密度、强调和业务能力结构，而非像素照抄 | Task 1 多模态提取 | 提取结果描述结构与意图，不包含照搬颜色或字体 |
| 学员能把参考意图写成可核对约束，并指出规则落在哪个页面元素 | Task 2 约束映射 | ≥3 条约束可从参考意图追溯到页面落点 |
| 学员能对参考内容作 Keep/Omit/Modify 裁决，并说明业务理由 | Task 3 裁决授权 | 能解释至少一项 Keep、一项 Omit 或 Modify 的业务理由 |
| 学员能在本地预览中做前后对比，用理由证明改变 | Task 4—5 重构与微调 | 前后差异可见、可复述、可追溯；业务路径没有因视觉修改而失效 |

概念分层：核心概念为项目级 Agent 约束 / Agent Harness、约束作用域与优先级、行为约束与设计约束、信息优先级与视觉层级、约束一致性验证；多模态参考提取、设计约束映射、Keep/Omit/Modify、视觉证据对比为操作方法；AGENTS.md/CLAUDE.md、DESIGN.md 和视觉证据为产物。安全红线横向管理，不占概念名额。

### 2.2 四步概念解析公式

#### 项目级 Agent 约束 / Agent Harness

1. **是什么 / 不是什么**：项目为 Agent 规定目标、范围、行为和设计规则的约束机制；不是单次 Prompt 或运行时硬控制。
2. **机制**：Agent 读取项目约束，主管核对关键红线和设计规则，再在授权范围内执行。
3. **当课操作例子与边界**：Task 2 检查并使用项目约束文件；约束能指导 Agent，但不等于运行时自动拦截，授权和验收仍由主管负责。
- **帮助理解的类比（可选）**：像给外协团队的项目章程：写明目标、范围和红线，但不替他们每步盯办；授权和验收仍由主管。章程不等于运行时自动拦截。
4. **交接价值**：回指 Task 2——约束文件要能说明 Agent 可以做什么、不能做什么，以及结果要满足什么。

#### 约束作用域与优先级

1. **是什么 / 不是什么**：规则按 项目级、目录级、文件级 分层适用，冲突时上一级压下一级；局部文件不能覆盖项目红线，也不是所有规则同层。
2. **机制**：先确认当前文件和任务落在哪个作用域，再按优先级处理冲突。
3. **当课操作例子与边界**：Task 2 先判断修改落在哪个项目、目录或文件，再按上级规则处理冲突；局部文件不能覆盖项目红线。
- **帮助理解的类比（可选）**：像公司规章、部门细则、单据模板的层级：局部细则不能覆盖公司红线。不是所有规则同层。
4. **交接价值**：回指 Task 2——主管能指出每条规则的适用范围和冲突处理顺序。

#### 行为约束与设计约束

1. **是什么 / 不是什么**：行为约束 = `CLAUDE.md`/`AGENTS.md`，规定 Agent 怎么工作（包管理器、文件边界、错误处理）；设计约束 = `DESIGN.md`，规定产物长什么样（间距、圆角、颜色层级）；两者都是项目级约定，不是代码级强制。
2. **机制**：Task 2 分别核对 DESIGN.md 的页面元素约束和 CLAUDE.md/AGENTS.md 的行为红线；一类文件不能替代另一类。 行为约束文件按工具分：Claude Code 读 `CLAUDE.md`、Codex 读 `AGENTS.md`；两个工具都用时，行为红线两边都要有（或在 `CLAUDE.md` 里用 `@AGENTS.md` 互引做单一真相源），否则一边静默看不到。
3. **当课操作例子与边界**：设计约束要指向具体页面元素，行为约束要覆盖包管理器、文件边界和错误处理；只写“做得好看”或“注意安全”都不够。
4. **交接价值**：回指 Task 2——两类约束都要可检索、可核对，不能停留在抽象描述。

#### 信息优先级与视觉层级

1. **是什么 / 不是什么**：按业务重要性安排内容、状态和操作的视觉强调；不是装饰偏好。
2. **机制**：逐项审视参考图中的每个元素，判断“保留并冻结现有业务内容”“参考图忽略项”“现有页面清理项”和“明确进行的视觉改进”。
3. **当课操作例子与边界**：Task 3 对每个参考意图做 Keep/Omit/Modify 裁决并写业务理由；参考图不能带入自己的业务内容。
4. **交接价值**：回指 Task 3——主管的裁决必须说明业务理由，不只是“好看”或“不好看”。

#### 约束一致性验证

1. **是什么 / 不是什么**：检查实现是否同时满足项目约束、设计约束和验收场景，并留下证据；不是只看文件存在。
2. **机制**：重构前截图作为基线，重构后截图作为对照，每处改变附理由；业务路径在视觉修改后仍可操作。
3. **当课操作例子与边界**：Task 4—5 对照重构前后截图、约束清单和业务路径；视觉变化没有理由，或页面路径不可操作，都标为未通过。
4. **交接价值**：回指 Task 4—5——主管验收时先确认业务路径仍可操作，再看视觉改善是否有理由支撑。

### 2.3 操作方法与交付产物

#### 操作方法

多模态参考提取、设计约束映射、Keep/Omit/Modify 和视觉证据对比是本课操作方法。

#### 交付产物

`AGENTS.md`/`CLAUDE.md` 承载行为约束，`DESIGN.md` 承载设计约束；视觉证据是验收产物。

### 2.4 扩展认识概念卡

#### 设计令牌（Design Token）（认识级）

把颜色、间距、字号等重复规则统一命名；教师一句话说明，不作为本课工程重点。

#### 版本节点（认识级）

保留批准前后候选差异的记录；不要求主管掌握 Git 命令。教师在 Task 3 前用 2 分钟说明每次大改前先存档，改崩后按确认范围恢复。

## 三、教学准备与安全边界

### 课前预检

- 第一课原型可用：学员已有一条可操作的业务路径和本地预览环境。
- 参考图就绪：学员已有第一课课后准备的视觉参考图；若无图片，指南提供三类原型的「文字版参考图卡」可替代（本课程不附带参考图图片文件）。
- `DESIGN.md` 存在且包含小写 CSS Tokens（如 `var(--art-primary)`）；`src/assets/styles/tailwind.css` 运行时变量可解析。
- `CLAUDE.md` 或 `AGENTS.md` 存在：确认项目根目录有行为约束文件（若不存在，教师在课前用 `/init` 生成基础版，包含包管理器约束、文件边界和错误处理原则）。
- 开发服务器可启动：`npm run dev`，本地预览 `http://127.0.0.1:8888/` 可访问（双击 `start-project.bat` 或运行 `npm run dev`）。
- Git 状态干净或有明确基线节点：教师演示前先 `git status` 确认。
- 助教理解环境问题 3 分钟接管规则，知道 CSS 变量大小写问题的现场处置方式。

### 实操前只讲四条红线

1. 只用 Mock/已脱敏数据，不输入真实资料、密钥、Token 或账号。
2. 视觉重构不增加业务功能、不新增第二条主路径；业务路径在视觉修改后必须仍可操作。
3. 不照搬参考图中的业务字段和数据；提取的是布局意图，不是业务内容。
4. 文字要求和主管确认是工作约束，不冒充运行时硬控制；Git 存档是安全网，不是自动审批。
5. 不要求主管手写 CLAUDE.md/AGENTS.md 全文；用 /init 生成后只核对行为约束是否覆盖关键红线（包管理器、文件边界、错误处理）。

教师不得虚构 `/design-lint`、`verify-project.ps1` 等课堂能力。实际运行什么，就展示什么证据。

## 四、90 分钟控场主线

| 时间 | 宏观阶段 | 教师动作 | 学员动作 | 阶段证据 |
| --- | --- | --- | --- | --- |
| 0—10 分 | **看见区别，建立模型** | 对比第一课粗糙原型与视觉重构版；用 Task 1—5 动作链和融合图讲五个概念 | 选定参考图，能指出"什么先被看到" | 知道本课成果与五者关系 |
| 10—25 分 | **教师完整示范** | 用统一案例串演 Task 1—5，只演方法，不让学员复现 | 观察四步闭环的完整动作 | 建立整体动作锚点 |
| 25—35 分 | **概念核对与裁决准备** | 提问核对五张概念卡；演示 Git 存档与 Discard Changes | 口头回答卡片；完成环境检查 | 概念理解和安全网就绪 |
| 35—80 分 | **学员实操** | 按 Task 1（约 10 分）→ Task 2（约 8 分）→ Task 3 裁决（约 12 分）→ Task 4 重构（约 10 分）→ Task 5 微调（约 5 分）巡视 | 完成提取、映射、裁决、重构和微调 | 个人视觉重构版原型 |
| 80—90 分 | **验收与闭合** | 指导前后对比验收，检查通过证据；收取随堂题 | 前后对比、核对证据与答案 | 原型线和主管线分别判定 |

压缩顺序：先取消个别展示，再压缩教师示范；不得删除个人实施、业务验收或主管判断。5 道必答题分散在相应 Task 后完成，最后只检查提交。

## 五、逐 Task 示范、口令、巡视与降级

教师统一案例只走一条路径：以工单看板为例，从参考图提取结构 → 映射设计约束 → Keep/Omit/Modify 裁决 → 受控重构 → 微调验收。每个 Task 均按以下四项执教。

### 课前准备：检查环境与阅读 DESIGN.md

- **教师示范**：点开 `DESIGN.md`，讲解 `src/assets/styles/tailwind.css` 字典映射为 `var(--art-primary)` 等小写变量；启动开发服务器确认本地预览可用。
- **教师口令**：`npm run dev`，打开本地预览确认第一课原型仍可操作。
- **巡视判断**：确认学员 `DESIGN.md` 配置正确无大写变量；本地预览可访问。
- **失败降级**：环境超过 3 分钟由助教接管；CSS 变量大写时现场更正为小写。

### Task 1：从参考图提取多模态布局与意图

- **教师示范**：用学员第一课的视觉参考图（或指南中的文字版参考图卡）演示多模态结构提取 Prompt 模板。强调“只提取布局和结构，不要使用参考图中的任何背景颜色、字体或杂乱样式”。
- **教师口令**：下发多模态结构提取 Prompt 模板，先不要修改代码，只输出分析结果。
- **巡视判断**：AI 输出是否描述首屏布局、主视觉焦点和次要信息排布；是否照搬了参考图的业务字段或颜色；是否在提取阶段就修改了代码。
- **失败降级**：AI 照搬业务字段时，指明"提取的是布局意图，不是业务内容"；AI 已修改代码时立即停止，要求回退到只输出分析。

### Task 2：把提取结果映射为设计约束

- **教师示范**：下发设计规范映射 Prompt 模板，展示如何将 Task 1 提取的结构与 `DESIGN.md` 进行映射。强调"不得虚构不存在的 Token，不得新建样式库。先不要修改文件，只输出映射方案"。然后展示核对 `CLAUDE.md`（或 `AGENTS.md`）的行为约束：确认包管理器约束（只用 npm 不用 yarn/pnpm）、文件边界（不碰 node_modules 和配置文件）和错误处理原则已覆盖。
- **教师口令**：下发 Token 规范映射 Prompt 模板，要求每条设计约束指向具体页面元素。同时核对 `CLAUDE.md`（或 `AGENTS.md`）的行为约束是否覆盖三条关键红线：包管理器、文件边界、错误处理。若文件不存在，用 `/init` 生成基础版后核对。
- **巡视判断**：所有样式是否显式映射到 `--art-*` 变量；设计约束是否指向具体页面元素而非抽象描述；是否虚构了不存在的 Token；`CLAUDE.md`/`AGENTS.md` 是否存在且覆盖三条行为红线。
- **失败降级**：虚构 Token 时指明只允许使用 `DESIGN.md` 已有变量；映射停留在抽象层时要求补充"落在哪个元素"；`CLAUDE.md`/`AGENTS.md` 缺失时用 `/init` 生成基础版；行为约束不全时补充缺失条款。

### Task 3：主管 Keep/Omit/Modify 裁决与授权

- **教师示范**：运行节点 1 存档指令 `git commit -m "baseline: before visual refactor"`，说明修改前后版本节点如何支持复核和按范围恢复。下发包含 Keep、Omit、Remove、Modify 四项裁决的提示词模板，示范 Discard Changes 的恢复边界。
- **教师口令**：发送主管裁决与授权提示词模板，在得到"同意方案，请开始修改代码"前不要修改文件。
- **巡视判断**：确认学员在下发修改口令前运行了 `git commit` 存档；裁决是否每项都有业务理由而非"好看/不好看"；是否授权了明确修改范围。
- **失败降级**：未存档就修改时先停止，补做存档再继续；裁决无业务理由时追问"为什么保留/为什么舍弃"；范围模糊时要求写清本轮 Modify 的具体项。

### Task 4：Agent 受控视觉重构与前后对比

- **教师示范**：发送“同意方案，请开始修改代码”口令，展示 Agent 执行一次受控重构。在 VS Code Git 视图中监视修改。刷新本地预览做前后对比。
- **教师口令**：只按裁决范围修改，不扩大；改完后报告实际修改文件和验收方法。
- **巡视判断**：Agent 是否只在授权范围内修改；是否误删了业务代码；业务路径是否仍可操作；前后差异是否可见。
- **失败降级**：改崩时右键文件选择 Discard Changes 1 秒物理撤销恢复；Agent 扩大范围时立即停止，回到裁决范围；业务路径失效时优先修复路径再修视觉。

### Task 5：微调、保存视觉证据与裁决记录

- **教师示范**：示范只做必要微调（如间距、对比度），运行节点 2 完结存档 `git commit -m "style: complete lesson 2 visual refactor"`。截屏保存至 `local-backups/lesson-02-evidence/`。
- **教师口令**：只修一个最影响理解或操作的问题，然后停止扩展；保存前后截图和裁决记录。
- **巡视判断**：微调是否只修一个问题而非全面重做；视觉证据是否保存；裁决记录是否与实际修改一致；`PROJECT_STATE.md` 是否更新。
- **失败降级**：微调引发新错误时停止自动修改，保留当前证据由教师接管；路径通过后再同步 `PROJECT_STATE.md`，不另设写作任务。

## 六、现场 Debug 与降级预案

| 问题类型 | 教师处置 | 禁止说法 |
| --- | --- | --- |
| 页面白屏或样式全部失效 | 检查 CSS 变量是否误写成大写 `var(--art-PrimaryBad)`，更正为小写 | "AI 自动修复了样式" |
| 改坏页面后找不到撤销按钮 | 指导在 VS Code 左侧第 3 个 Git 分支视图中右键文件选择 Discard Changes | "改坏了就只能重来" |
| 参考图选择不当或照搬业务字段 | 换一张与学员业务更相关的参考图；强调提取布局意图而非业务内容 | "参考图里有什么就做什么" |
| 重构后业务路径失效 | 优先修复业务路径，再修视觉；一次只修一个问题 | "好看比能用重要" |
| Agent 自行扩大修改范围 | 立即停止，回到 Task 3 裁决范围；用 Discard Changes 回滚超出部分 | "Agent 比主管更懂怎么改" |

## 七、随堂测试、通过标准与课后任务

### 两条线分别通过

- **原型线**：业务路径没有因视觉修改而失效；前后差异可见；数据标识仍清楚；不以页面数或视觉精致度单独评分。
- **主管线**：能解释至少一项 Keep、一项 Omit 或 Modify 的业务理由；≥3 条约束可从参考意图追溯到页面落点。
- `PROJECT_STATE.md` 只作交接，不能抵消任何一条主线的未通过。

### 必答题（5 题）

1. 从参考图提取布局意图时，应该提取什么、不应该提取什么？
2. 设计约束映射要求每条约束指向什么？为什么不能停留在抽象描述？
3. Keep/Omit/Modify 裁决中，至少一项裁决需要说明什么才算有效？
4. 视觉证据基线要求用什么证明改变，而不只靠什么？
5. 为什么视觉重构前必须先 Git 存档？Discard Changes 的作用是什么？

参考要点：提取结构与意图不照搬业务字段颜色；指向具体页面元素；业务理由而非主观审美；前后对照和理由而非"更好看了"；存档是安全网，Discard Changes 是文件级无损撤销。

### 拓展题（选做，2 题）

1. 用 Task 3 的一个真实页面元素说明 Keep/Omit/Modify 各一项裁决及其业务理由。
2. 简述 Git 存档（Save）与 Discard Changes（Load）的物理对应关系。

### 课后任务

10—15 分钟：在 `PROJECT_STATE.md` 中补齐本次设计约束和裁决记录；找一句你仍说不清的业务问题，留给下一课。不继续开发功能。
