# 第十课学员指南——双重交付终局与部门日常 Agent 赋能落地清单

> **核心思想：求真交付胜过虚假繁荣，严守红线重于盲目上线；双重通道因地制宜收口，人在回路筑牢责任底线；客观挑刺坦陈生产差距，扎实规程开启周一赋能。**

## 一、先看懂：终局双重交付与日常实战赋能

### 1.1 先看一个反差

在开始今天的结业实操前，请对比以下两种截然不同的交付方式带来的巨大风险落差：

| 虚浮自嗨的交付方式（全网叫停、丧失信誉） | 实事求是的工程化交付（赢得敬畏、扎实落地） |
| :--- | :--- |
| **成果宣称**：通篇宣称“原型已全自动运行、完全替代人工、下周即可全网直接上线”，对技术团队宣称“我们部门不需要你们 IT 了”。 | 明确附带《非生产就绪代码声明》，将原型定位为业务逻辑验证的“样板间”；坦诚列出八大生产就绪缺口，作为向 IT 部门立项的高质量输入。 |
| **成熟度标注**：通篇把 Mock 模拟数据、静态页面或假数据直接标成“全链路已证实通过”，隐瞒未做并发测试与异常断网的事实。 | 严格采用五类成熟度状态（已证实 / 仅 Mock 模拟 / 未验证 / 明确未实现 / 单机依赖边界），Mock 模拟一律如实打标，不伪装成功。 |
| **评估与整改**：对漏洞视而不见，或者让大模型“帮我把漏洞全自动改掉”，大模型直接生成越权的自动放行代码，主管丧失风控责任。 | 课前运行 `/evaluate` 冷酷挑刺；业务主管用足 10 分钟亲笔手写做出 HITL 商业裁决（追加门禁 / 划入非目标），坚决不让 AI 越权代做主。 |
| **结业汇报答辩**：台上满嘴跑火车，大谈“每周帮部门节省 50 小时、每年降本数百万”，提问被技术专家一戳即穿，立项被一票否决。 | 严格在 2–3 分钟内实事求是汇报，3 页 PPT 精炼交代痛点、差距与红线；明确周一工位安全试水第一责任人（Owner），务实求真。 |

今天你将通过双轨实操，完成从代码沙盘到工位实战的终极收口，成为一名**懂边界、敢暴露差距、能扎实赋能日常工作**的合格业务主管。

### 1.4 五个必须掌握的核心概念

#### 1. 原型 ≠ 生产系统（样板间不是交付住房）
- **是什么**：原型只用于在受控沙盘中验证业务逻辑是否闭环、功能切片是否值得投入；生产系统则必须具备企业级高可用架构、安全合规审计、真实数据库与鉴权体系对接、容灾备份与持续运维监控。原型使用了大量 Mock 模拟数据与受控环境，缺少生产级工程防御。
- **怎么用**：在所有交付物显著位置强制附带《非生产就绪代码声明》；将原型作为向技术团队立项的高质量输入材料，而不是要求 IT 直接上线的生产系统。
- **避坑红线**：严禁拿着跑通的原型要求技术人员“下周直接上线”；严禁隐瞒原型的工程缺陷与技术负债。

#### 2. 风险红线与非目标（确定不做比盲目去做更重要）
- **是什么**：明确圈定当前系统坚决不做的高危功能、坚决不接入的敏感数据以及坚决拒绝 AI 介入的法定义务节点（如大额资金划转、对外正式发函、特种资质终审）。
- **怎么用**：在交付清单首要章节设立独立的“非目标清单”与“AI 介入红线表”，为每个红线环节设立强制人在回路（HITL）审批门禁与熔断规则。
- **避坑红线**：严禁为了迎合领导将所有功能写满；严禁在缺乏风控审计的情况下尝试让 AI 全自动闭环高危动作。

#### 3. 综合评估与人在回路（Evaluate & HITL Remediation）
- **是什么**：由独立评估工具 `/evaluate` 对全量成果进行客观挑刺，暴露隐藏脆弱点；由承担最终管理与法律责任的人类主管（HITL）亲自对漏洞做出商业权衡与整改决断。
- **怎么用**：课前前置运行 `/evaluate` 获取客观缺陷清单，课内核对后亲笔手写裁定整改方案（如追加门禁、划入非目标、指定责任人），严禁大模型越权代写决策。
- **避坑红线**：严禁让大模型替主管做主；严禁对评估发现的高危漏洞视而不见或静默放行。

#### 4. 双重交付通道（IT 启动包 vs 工位单机工具包）
- **是什么**：业务原型在训练营终局收口时的“二选一”交付路径——交付 IT 架构立项的《产品决策与开发启动包》（通道 1）vs 面向工位自治闭环的《工位自用单机工具包》（通道 2）。
- **怎么用**：根据业务原型的系统定位与 IT 承接能力科学选定通道（A/B/C 类默认走通道 1 交付 IT 架构；D 类或科室内部小工具走通道 2 沉淀工位闭环），双轨资产分别依托标准化模板导出。
- **避坑红线**：单机自用必须严守“非生产代码声明”与四项安全红线，严禁把工位自用包装为生产系统直接上线，严禁将高危跨部门流程私自作为单机工具运行。

#### 5. 责任交接与落地清单（责任清晰转移与工位赋能）
- **是什么**：将原型的技术资产、业务规则、审批门禁与日常运行维护责任，明确移交给具体组织或个人的制度化动作；载体为《部门日常 Agent 赋能落地清单与认证工具包》。
- **怎么用**：逐项为业务规则、数据准确性、模型接口与异常兜底指派清晰的第一责任人（Owner）；载明下周一晨会安全试水具体工位与脱敏数据样本。
- **避坑红线**：严禁一句“交给 IT 了”或“大家日常用”模糊带过；交接是责任的清晰转移，绝不是责任消失。

#### 扩展认识
1. **生产就绪缺口分析（八大生产门禁 · 认识级）**：真实数据库对接、网络鉴权隔离、高并发容灾、自动化监控告警、数据备份回滚、法务隐私审计、降级人工兜底、日常运维第一责任人；
2. **抽签答辩与求真防吹法（认识级）**：现场随机抽签 3–5 名代表上台汇报（限时 2–3 分钟），其余学员同步提交；答辩只看已证实证据链与坦诚的生产差距，严禁无依据的商业 ROI 吹嘘，凡弄虚作假者评审一票扣 30 分。

### 4.1 认知误区与纠偏对策 (`misconceptions`)

| 误区编号 | 典型错误认知 | 纠偏正解与实战对策 |
| :--- | :--- | :--- |
| **M-01** | “原型跑通了，证明我们部门不需要 IT 了，下周直接把它部署上线” | 样板间绝不是交付住房！原型缺乏高可用、安全鉴权与并发容灾，直接上线必引发生产数据崩溃灾难。 |
| **M-02** | “给 IT 写的交接清单里，尽量别提没做完的和报错的，免得被 IT 刁难不给立项” | 隐瞒缺口是严重的渎职！诚实暴露未完成项与生产差距，才能帮助 IT 准确评估排期与架构改造工作量。 |
| **M-03** | “答辩一定要把 ROI 吹大，比如写‘每年帮部门节省 500 万成本、全自动替代 5 个人’” | 严禁画大饼！虚浮吹嘘只会丧失专业信誉；结业答辩一票否决虚假商业谎言，只认可实事求是的证据链。 |
| **M-04** | “`/evaluate` 找出的漏洞，直接让大模型帮我全部自动改好、自动决定怎么处理就行” | 绝不能放弃主管终审权！AI 不懂部门利益与法规红线，漏洞整改裁决必须由人类主管亲笔手写决断。 |
| **M-05** | “交接就是‘把包甩给 IT’，以后系统出了 Bug 或者算错钱都是 IT 的责任，跟业务主管无关” | 交接是责任的明确划分而非消失！业务规则与审批放行的最终责任始终属于业务主管，严禁甩锅。 |

### 5.3 随堂自测题（检验交付本质）

#### 必答题（5 题）
1. **原型与生产系统有什么本质区别？为什么原型跑通绝不等于能直接上线？**
   - *要点*：原型是低成本验证逻辑的样板间，缺少高可用、安全鉴权与并发容灾；生产系统需要通过严格的工程审计与架构保障，跑通原型绝不等于具备生产上线资格。
2. **在交给 IT 或向管理层交付时，为什么“明确非目标和风险红线”比“把功能列表写得满满当当”更有价值？**
   - *要点*：功能写满常隐藏未验证隐患与伪需求；明确非目标划定了系统安全底线，阻断了无效开发浪费，保护了企业核心资产。
3. **为什么要用 `/evaluate` 专门出具“漏洞与改进清单”？为什么整改决断必须由人类主管（HITL）亲笔做出？**
   - *要点*：`/evaluate` 能跳出开发者盲区进行冷酷挑刺；但 AI 不承担商业后果与合规责任，整改决断本质是商业权衡与责任确权，必须由人类主管亲自拍板。
4. **为什么本课要设计“双重交付通道（IT 启动包 vs 工位单机工具包）”？两者分别适合什么样的业务场景？**
   - *要点*：企业 IT 资源有限；通道 1 面向跨部门核心系统走正规立项，通道 2 面向科室自治轻量工具沉淀工位闭环生产力，实现因地制宜交付。
5. **责任交接要求什么？为什么交接是“责任的清晰转移”而不是“责任消失”？**
   - *要点*：交接要求逐项落实业务规则、数据脱敏、模型接口与异常兜底的第一责任人（Owner）；交接是明确 IT 与业务的权责分工，责任绝不会凭空消失。
