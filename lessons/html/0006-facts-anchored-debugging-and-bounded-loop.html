Lesson 06 · 用事实找 Bug，在边界内修复

学会定位和修复问题

排错前先存档，不盲猜、先断言；日志脱敏写报告，两轮不通安全熔断。
掌握 事实卡与五层诊断、日志脱敏与 DEBUG_REPORT 落盘 与 Checkpoint 和本课两轮上限！

🎯 本课目标：① 掌握排错前保存 Checkpoint 并唤醒 `$diagnose`，构建可核对的 PASS/FAIL 反馈闭环；② 掌握五层诊断卡口语化排查与落盘 `docs/LESSON_06_DEBUG_REPORT.md`；③ 掌握“2 轮硬熔断机制”，在自修 2 轮未 PASS 时停止自动修改，由指定人员按确认范围恢复 Checkpoint。

01 找 Bug 为什么不能靠猜？

原型有了、契约有了、智能薄片也有了——但页面打开是白屏，按钮点了没反应。让 Agent 自己反复改？两轮没修好反而越改越乱。第六课解决的就是"怎么从事实出发找 Bug，在边界内修复，修不好就停下来交给合适的人"。

记住这句话：
不盲目让 Agent 反复试，而是从复现、输入、契约、日志和实际状态缩小原因。一个故障、一个主假设、最多两轮——失败也必须留下证据。

排错不是比谁改得快，而是比谁的证据链完整、谁的停止判断准确。

03 核心概念卡：本课必须掌握的概念

本课必须掌握的核心概念 (点击展开详情)：

操作方法：事实锚定排错与五层诊断；它们支持核心概念落地，不替代事实、根因、边界、预算和处置概念。

1. 事实、假设与生成错误
📌 是什么 / 不是什么：实际观察、待验证解释和模型凭空补全必须分开记录；事实是看到的现象，假设是对原因的解释，生成错误是 AI 编造的不存在信息。三者不能混为一谈。
⚙️ 怎样运作：遇到故障时先记录可观察事实（页面报什么、数据是什么），再提出待验证假设（可能是 X 层的问题），最后警惕生成错误（AI 声称"已修复"但实际没改或改错了）。
🧭 当课操作例子与边界：Task 1—2 的事实卡只记录页面、数据和日志中实际看到的内容；诊断报告中的原因仍标为假设，Agent 自称“已修复”但没有证据时要当作生成错误。
💡 帮助理解的类比（可选）：像业务事故快报把“已发生的事实”“待核实的原因”和“未经证实的说法”分栏记录，三栏不能互相冒充。
2. 根因与表象
📌 是什么 / 不是什么：表象是可见症状，根因是造成症状的更深层原因；修掉错误文字不代表问题解决。
⚙️ 怎样运作：对照业务规则、数据来源和组件行为验证根因。
🧭 当课操作例子与边界：Task 1—3 先复现并记录事实，再用五层报告缩小范围；没有能证伪的主假设和证据，不授权修改。
💡 帮助理解的类比（可选）：像事故调查：先封锁现场、取证据、定因，再决定怎么修；不是看一眼报错就动手改。
3. 重试预算 / 熔断
📌 是什么 / 不是什么：为自动重试设定次数、时间或风险上限，达到阈值就停止；不是固定数字，也不是定位问题的五层标签。
⚙️ 怎样运作：每轮记录动作、观察和成本，达到预算后停止、升级或恢复。本课为保证证据和安全，Agent 诊断/修复最多进行两轮。
🧭 当课操作例子与边界：Task 2 先定位主假设，Task 3—4 记录每轮实际修改和验证结果；超过两轮或触发风险条件就进入 Task 5。
💡 帮助理解的类比（可选）：像客服升级：同一问题自动重试有次数上限，超过就停并转给指定人；不是让机器一直试到好为止。
4. 有界排错
📌 是什么 / 不是什么：明确一个故障、一个主假设、修改范围和轮次上限；失败也必须留下证据。不是无限试错，也不是一轮失败就放弃。
⚙️ 怎样运作：排错前先存 Checkpoint 存档，限定修改范围，设置最多两轮修复上限；第一轮按主假设修复，验证不通过则调整假设进行第二轮，仍未通过则停止。
🧭 当课操作例子与边界：Task 3—4 先保存 Checkpoint，再按主假设修改；第一轮验证不通过才调整假设做第二轮，仍不通过就停止，不继续扩大范围。
💡 帮助理解的类比（可选）：像动手修前先拍照存档、限定只改这一处、最多试两轮，不行就停并交出证据；不是无限试到修好。
5. 停止、升级与恢复
📌 是什么 / 不是什么：证据不足、风险越界或两轮无进展时停止，由指定人员接管或按范围恢复；不是失败放弃，也不是让 Agent 继续试。
⚙️ 怎样运作：停止时记录原因（证据不足/风险越界/两轮无进展）、新证据需求、恢复责任人；恢复时从 Checkpoint 存档回退，导出 .patch 快照备份，不无差别清空。
🧭 当课操作例子与边界：Task 5 记录停止原因、新证据需求和恢复责任人；恢复只能按确认范围进行，不能用无差别清空代替交接。
💡 帮助理解的类比（可选）：像设备异常后的停机交接：达到停止条件就保留现场、记录原因和所需证据，再交给明确责任人处理。它不是继续碰运气，也不是把问题一键清空。

05 学员实操 Task 1 ~ Task 5 自然授权口令卡

Task 1：激活 $diagnose，确认故障现象，审查 Agent 的事实报告
我已确认故障现象存在（看了一眼页面）。现在激活 $diagnose Skill，请按 Phase 1—2 执行： 1. 构建可重复的 PASS/FAIL 信号 2. 复现预置故障 3. 生成一张事实卡，只记录可观察事实（页面报什么、数据显示什么、控制台报什么） 4. 不要写猜测原因（那是假设，下一步再做） 5. 不要修改任何代码 6. 日志中有敏感信息（Token、Key、账号）的先脱敏为 事实卡格式： - 故障现象：（只写看到什么） - 复现步骤：（怎样触发） - 控制台信息：（脱敏后第一行报错，如有） - 数据状态：（字段值是什么）
🎯 预期输出：AI 输出了一张事实卡，只记录可观察现象，不含猜测或编造，没有修改代码。你审查事实卡后确认只含现象，签确认。
Task 2：审查 Agent 的五层诊断报告，选定一个可证伪主假设
$diagnose 已激活，请按 Phase 3 执行五层诊断。 故障现象：【粘贴 Task 1 的事实卡】 按以下口语标签逐层检查，从 Layer 1 开始逐层排除： - Layer 1 环境：网页跑得起来吗？ - Layer 2 数据：有数据吗？拿到的是 null 吗？ - Layer 3 状态：数据变了界面动了吗？ - Layer 4 日志：控制台第一行红字报什么？（脱敏后） - Layer 5 契约：字段名和契约配得上吗？ 输出： 1. 每层的排查结论（PASS / FAIL / 不适用） 2. 定位到最可能的问题层（只选一层） 3. 生成 3—5 个可证伪假设并排序，标明最可能的主假设 不要同时提多个主假设。不要修改代码。
🎯 预期输出：AI 逐层排查后定位到一层，生成了排序的假设列表并标明主假设，没有修改代码。你审查报告后确认定位合理，选定主假设。
Task 3：存 Checkpoint，审查 Agent 的修复方案，核对范围后授权
排错前先存 Checkpoint 存档。$diagnose 已在运行中，请按 Phase 4—5 执行： 1. 运行 git commit -m "checkpoint: before lesson 6 debug" 存档 2. 读取最小证据：只读契约文件和故障相关的页面代码 3. 确认主假设（字段名与契约不一致） 4. 提出修复方案：只改一个字段名，不碰其他文件 5. 等待主管核对范围后才执行修改 不要扩大修改范围。不要读取不必要的文件。不要重新激活 $diagnose。
🎯 预期输出：AI 先存了 Checkpoint，读了契约和页面代码，提出了一个只改字段名的修复方案，等待你核对。你审查方案后确认范围没有扩散，授权执行。
Task 4：验证结果，必要时进行第二轮，否则停止
请验证修复结果。 1. 刷新本地预览，观察故障是否消失 2. 基于实际观察（不是 AI 自称"已修复"）判断： - 通过：故障现象消失，进入 Task 5 记录 - 不通过：调整假设，进行第二轮修复（仍限定范围） - 两轮都不通：停止，记录停止原因 不要继续试第三轮。不要相信"AI 说修好了"，必须实际看效果。
🎯 预期输出：AI 刷新了页面，基于实际观察判断通过或不通过，没有自称"已修复"就算数。
Task 5：记录修复后状态，或记录停止/升级原因和恢复责任人
请帮我完成诊断与修复/停止证据包，写入 docs/LESSON_06_DEBUG_REPORT.md。 证据包必须包含以下六项： 1. 事实卡：（Task 1 的可观察现象） 2. 主假设：（Task 2 的可证伪主假设） 3. 诊断过程：（五层排查结论，定位到哪一层） 4. 修复结果：（改了什么，验证是否通过）或 停止原因：（两轮无进展 / 证据不足 / 风险越界） 5. 新证据需求：（如果停止，需要什么新证据才能继续） 6. 恢复责任人：（谁来接手，名字和角色） 如果修复成功：记录修复结果和恢复责任人。 如果停止：记录停止原因、新证据需求和恢复责任人。
🎯 预期输出：LESSON_06_DEBUG_REPORT.md 包含六项完整内容，事实和假设分开记录，停止时有停止原因和恢复责任人。

2. 💡 常见概念误区与正确理解 (3 栏对照表)

常见误区 (Misconception) 正确硬核理解 (Correct Engineering Reality) 如何纠偏与护栏防护 (Remedy & Guardrails)
误区 1
"遇到报错就把完整日志贴给 AI"		 日志中有 Token 和密钥，必须先脱敏为 再给 AI 树立正确工程意识，严格遵循护栏规范。
误区 2
"控制台全是红字肯定是我把系统搞砸了"		 控制台长堆栈是框架链式抛错，只需看第一行 Error Message，长堆栈留给 AI 树立正确工程意识，严格遵循护栏规范。
误区 3
"git restore 会把我之前写的代码全抹掉"		 排错前先存 Checkpoint，回滚只清除坏修补，历史代码毫发无损 在 VS Code 界面点击 Discard Changes 实现单个文件无损撤销。
误区 4
"AI 说已修复就是修好了"		 必须实际刷新本地预览看效果，不看 AI 自称结果 树立正确工程意识，严格遵循护栏规范。
误区 5
"两轮不通再试一轮就好了"		 两轮不通就停止，记录原因和恢复责任人，不继续盲目试 树立正确工程意识，严格遵循护栏规范。

2. 🎯 课后退场自测题 (Exit Ticket)

❓ 退出门禁题 1：事实、假设和生成错误有什么区别？为什么排错时必须分开记录？
参考答案解析：
事实是观察现象、假设是待验证解释、生成错误是编造。分开才能追溯——混淆后无法判断哪条信息可信，也无法向 IT 交接。
❓ 退出门禁题 2：五层诊断卡的五层分别是什么？为什么要从上到下逐层排除而不是到处乱改？
参考答案解析：
环境/数据/状态/日志/契约五层。逐层排除缩小范围，避免到处乱改扩大问题；跳层排查容易遗漏浅层问题。
❓ 退出门禁题 3：有界排错要求明确哪四项？为什么不能无限试错？
参考答案解析：
一个故障、一个主假设、修改范围、轮次上限。不能无限试错因为每轮试错可能扩大问题，且没有明确停止条件就无法交接。
❓ 退出门禁题 4：两轮诊断仍未通过时应该怎么做？为什么不能继续试第三轮？
参考答案解析：
停止并记录停止原因、新证据需求和恢复责任人。不能继续试第三轮因为两轮无进展说明当前证据不足，继续试只会扩大风险。
❓ 退出门禁题 5：停止、升级与恢复分别是什么意思？停止时至少要记录哪三项？
参考答案解析：
停止是暂停排错，升级是交给更合适的人，恢复是从 Checkpoint 回退。停止时至少记录停止原因、新证据需求和恢复责任人。
三句话带走 (Key Takeaways)：
  1. 排错前保存 Checkpoint；未通过的本轮改动按确认范围恢复，已确认基线保留。
  2. 控制台报错不慌张，只提取第一行 Error 事实，日志脱敏 `` 落盘 DEBUG_REPORT。
  3. 修不过去不硬撑，2 轮未 PASS 自动触发硬熔断；指定人员按确认范围恢复 Checkpoint。
