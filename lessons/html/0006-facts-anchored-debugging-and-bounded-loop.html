01 找 Bug 为什么不能靠猜？

原型有了、契约有了、智能薄片也有了——但页面打开是白屏，按钮点了没反应。让 Agent 自己反复改？两轮没修好反而越改越乱。从本课起，课程全面推行 35+35+10+10 双轨制：不仅教你在代码沙盘中用事实定位代码故障，更将“说法-物证对照”的心智平移至企业日常管理，开展《签发前核验与裁决单》实战！

⚖️ 双轨考核互不顶替铁律：
轨道 A（代码沙盘排错 · 35 min）：五层诊断定位，Checkpoint 存档，2 轮预算内完成有界单点修复；
轨道 B（管理签发核验 · 35 min）：逐条对照说法与物证，剔除道德臆测，签署《签发前核验与裁决单》；
两线分别考核、互不顶替。到点立即准时硬切轨道，捍卫日常管理实操时间！

排错不是比谁改得快，而是比谁的证据链完整、谁的停止判断准确、谁能在管理签字时守住事实底线。

03 核心概念卡：本课必须掌握的概念

本课必须掌握的核心概念 (点击展开详情)：

操作方法：事实锚定排错与五层诊断；它们支持核心概念落地，不替代事实、根因、边界、预算和处置概念。

1. 说法-物证对照 (Say-vs-Evidence Mapping)
📌 【是什么】将待签材料中的所有陈述（时间、动作、责任、系统状态）逐条拆解，在客观物证（单据、日志、时间戳）中寻找对应证据的比对方法。
⚙️ 【怎么用】将陈述标注为三类：物证支持（给出证据出处）、无物证（归入待验证假设）、与物证矛盾（标红并给出反证）。
🚨 【避坑红线】严禁把口头汇报或推测当成事实；严禁 Agent 编造不存在的单据与日志。
2. 根因定位与五层诊断
📌 【是什么】按“环境层 → 数据层 → 状态层 → 日志层 → 契约层”逐级排查问题的诊断方法。
⚙️ 【怎么用】提出一个有明确验证依据的推断，按层搜集证据；推断被推翻立刻更换方向。
🚨 【避坑红线】严禁看到界面报错就胡乱修改代码，没有定位到具体层级之前禁止动手。
3. 重试预算与熔断
📌 【是什么】为自动修复设定的次数上限（如最多 2 次），达到阈值强制停止。
⚙️ 【怎么用】防止 AI 在错误思路上越陷越深，保护上下文干净，及时触发人工介入。
🚨 【避坑红线】严禁解除重试限制，盲目重试不仅浪费成本，还会造成代码大面积污染。
4. 有界排错 (限时限范围)
📌 【是什么】锁定单一问题、限定修改范围、设定最多只试两轮的止损排查机制。
⚙️ 【怎么用】排错前先存快照，第一轮不通调整思路试第二轮，两轮仍未解决立即停机转人工。
🚨 【避坑红线】严禁放任 AI 无限试错，两轮无进展时必须导出补丁快照并恢复现场，绝不扩大破坏面。
5. 签发前核验与裁决单 (Pre-signature Verification)
📌 【是什么】主管在向外部或高层签发呈批件/事故报告前，建立的结构化物证审查与责任裁决底稿。
⚙️ 【怎么用】依托 student-package/templates/SIGNOFF_VERIFICATION_TEMPLATE.md 导出核验报告，完成事实认定与处置签署。
🚨 【避坑红线】严禁盲目信任下属递交的一面之词；核验底稿严禁带有道德评判与主观臆断。

🚀 轨道 A：沙盘技术排错 (Tasks 1–2 · 建议限时 35 min)

在本地受控沙盘中，运用五层诊断与有界排错自修循环，定位预置故障并完成单点修复。

Task 1：激活 $diagnose，确认故障现象，审查事实报告
我已在本地预览确认页面故障存在。现在激活 $diagnose，请按 Phase 1—2 执行： 1. 检查当前本地开发服务（127.0.0.1:8888）与页面可见状态； 2. 生成一张事实卡，严格只记录可观察事实（页面报什么、数据显示什么、控制台报错第一行）； 3. 严禁写入任何猜测原因（假设下一步再做）； 4. 严禁修改任何代码文件； 5. 日志中若出现 Token/Key 等敏感信息，必须脱敏为 <REDACTED>。 输出格式： - 故障现象：（肉眼看到什么） - 复现路径：（点击哪一步触发） - 控制台关键信息：（脱敏后第一行） - 数据状态：（组件接收到的具体字段名与值）

批准上述修复范围。请执行单点修复，并自动刷新验证结果。若 1 轮未通过，允许微调假设再试 1 轮；若 2 轮仍未通过，必须立即停止并报告！

2. 💡 常见概念误区与正确理解 (3 栏对照表)

常见误区 (Misconception) 正确硬核理解 (Correct Engineering Reality) 如何纠偏与护栏防护 (Remedy & Guardrails)
误区 1
"遇到报错就把完整日志贴给 AI"		 日志中有 Token 和密钥，必须先脱敏为 再给 AI 树立正确工程意识，严格遵循护栏规范。
误区 2
"控制台全是红字肯定是我把系统搞砸了"		 控制台长堆栈是框架链式抛错，只需看第一行 Error Message，长堆栈留给 AI 树立正确工程意识，严格遵循护栏规范。
误区 3
"git restore 会把我之前写的代码全抹掉"		 排错前先存 Checkpoint，回滚只清除坏修补，历史代码毫发无损 在 VS Code 界面点击 Discard Changes 实现单个文件无损撤销。
误区 4
"AI 说已修复就是修好了"		 必须实际刷新本地预览看效果，不看 AI 自称结果 树立正确工程意识，严格遵循护栏规范。
误区 5
"两轮不通再试一轮就好了"		 两轮不通就停止，记录原因和恢复责任人，不继续盲目试 树立正确工程意识，严格遵循护栏规范。

2. 🎯 课后退场自测题 (Exit Ticket)

❓ 退出门禁题 1：事实、假设和生成错误有什么区别？为什么排错时必须分开记录？
参考答案解析：
事实是观察现象、假设是待验证解释、生成错误是编造。分开才能追溯——混淆后无法判断哪条信息可信，也无法向 IT 交接。
❓ 退出门禁题 2：五层诊断卡的五层分别是什么？为什么要从上到下逐层排除而不是到处乱改？
参考答案解析：
环境/数据/状态/日志/契约五层。逐层排除缩小范围，避免到处乱改扩大问题；跳层排查容易遗漏浅层问题。
❓ 退出门禁题 3：有界排错要求明确哪四项？为什么不能无限试错？
参考答案解析：
一个故障、一个主假设、修改范围、轮次上限。不能无限试错因为每轮试错可能扩大问题，且没有明确停止条件就无法交接。
❓ 退出门禁题 4：两轮诊断仍未通过时应该怎么做？为什么不能继续试第三轮？
参考答案解析：
停止并记录停止原因、新证据需求和恢复责任人。不能继续试第三轮因为两轮无进展说明当前证据不足，继续试只会扩大风险。
❓ 退出门禁题 5：停止、升级与恢复分别是什么意思？停止时至少要记录哪三项？
参考答案解析：
停止是暂停排错，升级是交给更合适的人，恢复是从 Checkpoint 回退。停止时至少记录停止原因、新证据需求和恢复责任人。
三句话带走 (Key Takeaways)：
  1. 排错前保存 Checkpoint；未通过的本轮改动按确认范围恢复，已确认基线保留。
  2. 控制台报错不慌张，只提取第一行 Error 事实，日志脱敏 `` 落盘 DEBUG_REPORT。
