用 grill-me 把主管的口语想法追问成可核对的业务、数据与验收约定，为第四课薄切片实施提供冻结输入。

01 为什么要先定义，再实施？

你已经有了一个可操作的业务原型和视觉约束。但如果问"你的原型到底解决什么问题、数据从哪来、怎样算通过"，你可能答不清楚——这正是第三课要解决的痛点。

记住这句话：
第三课只完成"定义正确"，不同时承担大规模实施。用 grill-me 把主管的口语想法追问成可核对的业务、数据与验收约定，为第四课薄切片实施提供冻结输入。

先定义清楚，后面每一课的切片、智能行为和验收才有锚点。跳过定义直接实施，就会失去可核对的范围和通过条件。

03 核心概念卡：四个必须掌握的概念

四个必须掌握的核心概念 (点击展开详情)：

操作方法：结构化追问（Grill-Me），用于把业务问题、契约和验收条件追问清楚，不占核心概念卡。

1. 业务问题边界
📌 【是什么】由明确的使用者、触发时机、核心痛点、交付目标与“明确不做项”共同划定的工作范围。
⚙️ 【怎么用】实操前写明本轮只解决什么、坚决不做什么，作为防范需求无休止膨胀的防火墙。
🚨 【避坑红线】严禁带着模糊的一句话需求开工，没有圈定非目标之前不得进入开发。
2. 业务契约
📌 【是什么】把业务目标、涉及角色、处理规则与验收标准白纸黑字写成确定性协议，不让 AI 凭空瞎猜。
⚙️ 【怎么用】作为主管与 AI、IT 团队之间的共同语言，让所有人在开发与验收时有据可依。
🚨 【避坑红线】严禁使用口头模糊描述，未冻结业务契约前禁止随意修改核心业务逻辑。
3. 数据契约
📌 【是什么】固定字段名称、类型、枚举、来源和缺失行为等数据结构约定。
⚙️ 【怎么用】建立界面与未来后端 API 之间的可追溯边界，确保前后端字段定义严密一致。
🚨 【避坑红线】未冻结数据契约前禁止随意构造杂乱假数据或在前端写死逻辑。
4. 验收场景 (Given-When-Then)
📌 【是什么】包含“前置条件（Given）+ 触发操作（When）+ 预期可见结果（Then）”的具象业务用例。
⚙️ 【怎么用】在动手前就把考核题目出好，既包含正常成功路径，也必须包含异常报错与降级路径。
🚨 【避坑红线】严禁写“功能好用/界面美观”等主观评价，验收标准必须是肉眼可见或日志可查的客观事实。
5. Skill (打包技能指令)
📌 【是什么】沉淀在项目中的标准化 SOP 操作指令包（SKILL.md），AI 装载后即可按既定规范与专业动作稳定执行。
⚙️ 【怎么用】不仅用于开发测试，主管更可以亲手定义属于自己部门的专属业务 Skill（如报销审核规则、客户线索评级等），固化老员工经验。
🚨 【避坑红线】严禁把临时随手写的一次性 Prompt 当作 Skill；真正的 Skill 必须包含清晰的输入、步骤、输出格式与防错约束。

04 阻断性待确认事项强校验门禁 (Fail-Closed Blocking Gate)

🛡️ 门禁机制规则 (Fail-Closed Blocking Gate)：
在 `grill-me` 追问过程中，若以下 6 项核心内容中任何一项包含 [待确认]，Agent 将输出 `BLOCKING_GATE_FAILED` 拒绝落盘文件，强行阻止带病进入第四课：
  1. 核心使用者与责任角色未明确；
  2. 核心字段来源未物理确认；
  3. 关键业务逻辑规则存在冲突；
  4. 敏感数据处理方式未定义；
  5. In Scope 边界线模糊不清；
  6. 缺失至少 1 个完整的 Given-When-Then 验收场景。

05 动手体验：`grill-me` 澄清与 Blocking Gate 强校验模拟

Task 1：选定最需要说清的一条业务路径
我要从现有原型中选定一条最需要说清的业务路径。 我的业务原型类型是：【A. 监控与决策型 / B. 任务与流程型 / C. 操作工具型】 我选定的路径名称是：【填写】 主要使用者是：【填写】 主要动作是：【填写】 预期结果是：【填写】 本轮明确不做：【填写】 请先不要读取项目文件，不要调用修改或运行工具，也不要创建任何文件。 请只复述我选定的路径，并指出你认为仍模糊、需要追问的内容。
🎯 预期输出：模型复述了你的路径，并标出仍模糊的内容，但没有声称已经看过项目或开始实施。
Task 2：用 grill-me 依次澄清六大要素
请使用 grill-me 技能帮我梳理需求。 我的业务原型类型是：【A / B / C】 我的业务痛点与一句话需求是：【填写你选定的路径和使用场景】 请按照 grill-me 规范，每次只问我 1 个最关键的问题，帮我理清： 1. 使用者与问题 2. 目标 3. 边界（本轮做什么、不做什么） 4. 风险（数据敏感度与错误代价） 5. 验收标准（怎样算通过） 6. 停止/升级条件（何时必须停下来请示） 在需求澄清完毕前，绝对不要修改任何代码与文件。
🎯 预期输出：AI 每次只问一个问题；你逐轮确认后进入下一题；追问覆盖了六大要素。
Task 3：收敛为业务功能卡，未确认项显式保留
请将前面的讨论成果汇总： 1. 拟定 Markdown 文档《业务功能卡》内容预览，包含： - User & Problem（使用者与问题） - Goal（业务目标） - Boundary（本轮做什么、不做什么） - Risk（数据敏感度与错误代价） - Acceptance（验收标准） - Stop / Escalation（停止/升级条件） - 未确认项必须显式标注"待确认"，不能悄悄删除。 2. 拟定 TypeScript 接口草稿（src/types/prototype-contract.d.ts） 与 Mock 种子数据（src/mocks/prototype-data.ts）的导出代码预览。 请只输出预览方案，等待我回复许可口令，严禁提前写入文件。
🎯 预期输出：Agent 先输出预览方案，等待你的许可口令后才落盘；业务功能卡包含六大要素；未确认项有"待确认"标注。
Task 4：固定字段字典、状态、Mock 样例和敏感度
基于刚才的对话，请帮我整理一份 Markdown 格式的《轻量数据契约卡》。 包含以下两部分： 1. 基础数据契约表： - 字段名称（英文字段名） - 业务含义（中文名称） - 数据类型（文本/数字/布尔/日期/枚举） - 是否必填 - 数据来源（固定为 Mock 数据） - 示例值 - 敏感等级（公开 / 内部 / 严禁发送 AI） 2. 针对我的原型类型的专属扩展契约： - 【监控决策型】：指标口径/计算公式、对比基准、异常阈值、下钻维度 - 【任务流程型】：发起/处理角色、业务状态机(草稿->待处理->已完成)、允许动作、驳回/撤销规则 - 【操作工具型】：输入结构、校验规则、处理逻辑、输出结构、HITL 人工确认点 先不要写入文件，仅输出内容方案预览呈报给我确认。
🎯 预期输出：字段字典与业务功能卡一致；敏感等级已标注（公开/内部/严禁发送 AI）；Mock 样例与字段类型匹配。
Task 5：写出 1—2 条可观察的验收场景，主管最终确认
基于业务功能卡和数据契约，请帮我写出 1—2 条可观察的验收场景。 每条验收场景包含： 1. Given（给定条件）：前置状态或数据存在 2. When（动作）：使用者执行什么操作 3. Then（可观察结果）：应观察到什么具体结果 同时请检查每条验收场景是否追溯到业务功能卡中的字段和规则。 如果遇到数据缺失或规则冲突，请说明应触发停止并升级给主管。 先不要写入文件，仅输出内容方案预览呈报给我确认。
🎯 预期输出：验收场景有具体条件、动作和可观察结果；追溯到功能卡；只有 1—2 条而非全面铺开；主管做了最终确认。

06 ✍️ 概念互动填空与 💡 常见误区 3 栏对照

1. ✍️ 概念互动填空 (Interactive Fill-in-the-Blanks)

请根据本课所学，在下拉框中选择正确的工程术语完成填空，并点击“核对答案”：

1. Prompting vs. Harness：盲发口头 Prompt 容易引发 AI 凭空脑补与需求漂移；通过 进行 3–5 分支、5–7 轮结构化追问，本质是将模糊需求转化为确定性的 。
2. Given-When-Then vs. Stop Conditions：基于场景的 Given-When-Then 用于判断 ；而 Stop Conditions 用于判断 。
3. 强校验门禁 (Fail-Closed Blocking Gate)：若使用者角色、核心字段来源、业务规则等存在 [待确认] 事项，grill-me 会输出 。

2. 💡 常见概念误区与正确理解 (3 栏对照表)

常见误区 (Misconception) 正确硬核理解 (Correct Engineering Reality) 如何纠偏与护栏防护 (Remedy & Guardrails)
误区 1
"直接发'帮我做个退款页面'最省事"		 模糊指令会导致 AI 凭空脑补字段与数据幻觉，后续接后端时项目直接崩溃。必须用追问范式（Grill-Me）逐题追问。 用追问范式（Grill-Me）逐题澄清，禁止脑补。
误区 2
"现在用的都是假数据，不需要标敏感度"		 敏感度标记是写给 IT 部门的交接契约，告知生产环境哪些真实字段不可送入 LLM。在数据契约表中必须显式标明敏感等级。 树立正确工程意识，严格遵循护栏规范。
误区 3
"遇到业务异常或数据缺失时让 AI 随意猜测 fallback"		 盲目静默掩盖报错会导致坏数据写入系统。在功能卡中明确定义停止/升级条件，异常时拉绳停机。 树立正确工程意识，严格遵循护栏规范。
误区 4
"AI 生成代码前不需要经过只读预览"		 直接让 AI 修改源码可能误删已有逻辑。执行 Task 3A 只读结构预览门禁，确认无误后再授权 Task 3B 写入。 树立正确工程意识，严格遵循护栏规范。
误区 5
"把所有部门需求一次性写成大而全 PRD 才完整"		 本课只围绕一条主路径说清。大而全 PRD 会让追问失焦，也无法在课内完成。 用追问范式（Grill-Me）逐题澄清，禁止脑补。

2. 🎯 课后退场自测题 (Exit Ticket)

❓ 退出门禁题 1：业务问题边界需要回答哪五个问题来限定本次业务？
参考答案解析：
使用者、触发、问题、目标和明确非目标共同限定本次业务。
❓ 退出门禁题 2：grill-me 追问和让 AI 无限提问有什么本质区别？
参考答案解析：
grill-me 是沿未决分支逐题澄清并得到主管确认，每次只问一个问题；无限提问是 Agent 自行发散，不经确认就脑补。
❓ 退出门禁题 3：业务契约固定了哪六个要素？未确认项应该怎么处理？
参考答案解析：
User & Problem、Goal、Boundary、Risk、Acceptance、Stop/Escalation 六个要素；未确认项必须显式标注"待确认"，不能悄悄删除。
❓ 退出门禁题 4：数据契约要求主管核对什么？TS 类型文件由谁来写？
参考答案解析：
主管核对字段含义、类型、枚举、Mock 样例和敏感等级等业务含义；TS 类型文件由工程师来写，主管不要求自己写。
❓ 退出门禁题 5：验收场景和功能名称列表有什么区别？写出一条验收场景需要哪三个部分？
参考答案解析：
验收场景用给定条件、动作和可观察结果说明怎样算通过；功能名称列表只列名称，无法判断是否通过。三个部分：Given（给定条件）、When（动作）、Then（可观察结果）。
❓ 退出门禁题 6：Skill 和一次性 Prompt 有什么区别？为什么 grill-me 是 Skill？
参考答案解析：
Skill 是可复用的打包指令（SKILL.md），把一套方法固化、跨项目重用；一次性 Prompt 是临时写的单次指令。grill-me 把“逐题追问”这套方法固化下来重复使用，所以是 Skill。
三句话带走 (Key Takeaways)：
  1. 先澄清 6 要素，清空阻断项，落盘 9 章节契约卡，最后才写代码。
  2. 分清 Given-When-Then 功能验收与 Stop Conditions Agent 熔断边界。
  3. `BUSINESS_FEATURE_CARD.md` 冻结为唯一基线，无后置静默需求变更。
