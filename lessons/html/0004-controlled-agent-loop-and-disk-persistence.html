Lesson 04 · 把契约切成一个可实施的薄片

把大需求拆成连续的小成功

不要让 Agent 一口气完成整个功能！通过 Plan & Execute 增量薄切片、Working Tree 版本证据 与 可追溯验收，掌控节奏并保留有界恢复路径。

🎯 本课目标：① 从第三课冻结契约中选择一个纵向薄片，完成可见实施并保留必要状态证据；② 先形成经主管确认的实施计划，再按计划执行和调整；③ 区分技术状态与业务状态，在实施前后分别确权；④ 主管按契约验收，记录候选版本与处置结果，不自动宣称通过。

01 为什么要切薄片而不是一次做完？

第三课把业务说清楚了，但如果直接把全部需求一次实施，Agent 会在大范围中失控——改了东墙塌西墙，90 分钟内什么都没完成。第四课解决的就是"怎么把大需求切成一个小到能做完、小到能验收的薄片"。

记住这句话：
第三课负责把事情说对，第四课负责把一小件事情做对。一次完成一条从输入到结果的纵向变化，不是把任务拆成没有业务结果的技术碎片。

只做一个薄片，做完验收，记录状态——这就是你在后续课程中反复使用的节奏。

03 核心概念卡：本课必须掌握的概念

本课必须掌握的核心概念 (点击展开详情)：

操作方法：Plan & Execute、两阶段版本记录、有界恢复；提交数量不固定。HITL 授权点属于扩展认识。

1. 薄切片 (纵向业务切片)
📌 【是什么】一次只做一条“从输入到看到结果”贯穿前台到后台的最小业务闭环。
⚙️ 【怎么用】按 3 条黄金标准把控：①业务贯通（1条完整线）；②时间可控（5-15分钟内完成）；③即时可验（能在本地点击走通，改错可一键回退）。
🚨 【避坑红线】严禁搞“只做了一半界面但点不动”的技术半成品，也严禁把几个页面的大功能打包成一个切片一口气做完。
2. 版本证据与回退快照 (Diff & Commit)
📌 【是什么】Diff（修改痕迹）就像 Word 审阅红绿划线；Commit（存档快照）就像单机游戏的存档点。
⚙️ 【怎么用】改动前存盘，改动后看 Diff 核对痕迹，验证通过后再做阶段性确认；一旦跑偏立刻一键回退到上个存档点。
🚨 【避坑红线】严禁连续让 AI 修改却不存盘；改错了严禁让 AI 在错误代码上打补丁，必须坚决回退重来。
3. 技术状态与业务状态
📌 【是什么】技术状态指程序维度的表现（页面崩没崩、控制台报不报错）；业务状态指商业逻辑的真相（算得对不对、流程走没走通）。
⚙️ 【怎么用】验收时必须双重视角核对：先看技术状态（页面能正常操作），再重点穿透核对业务状态（数据增删改查是否符合商业规则）。
🚨 【避坑红线】技术状态正常（无红字报错）绝不等于业务状态正确！界面能点通可能只是展示了静态假数据，必须亲手走通真实逻辑。
4. 可追溯验收
📌 【是什么】把验收场景、操作、观察、原始证据、结论和责任关联到具体版本，让 IT 能复核主管批准了什么。
⚙️ 【怎么用】每通过一个切片，在 PROJECT_STATE.md 中记录对应的 Commit 哈希、验收截图与主管签字。
🚨 【避坑红线】严禁口头验收或把简单的测试跑通误当业务验收；没有版本证据关联的修改一律无效。
5. 两阶段版本记录与有界恢复
📌 【是什么】第一阶段记录候选改动与修改痕迹（未确认）；第二阶段记录主管核验后的验收结论与处置记录。
⚙️ 【怎么用】两阶段严格分离，验证通过存第二阶段，验证失败导出 .patch 补丁并一键恢复 Clean 工作区。
🚨 【避坑红线】严禁把未经验收的候选改动直接作为最终版本；改错时绝不放任脏工作区累积。

05 学员实操 Task 1 ~ Task 5 自然授权口令卡

Task 1：校验第三课契约，确认可独立验收的路径
请读取我的业务功能卡（docs/BUSINESS_FEATURE_CARD.md）和数据契约， 确认 2—3 条可独立验收的路径。 每条可验收路径需要写清： 1. 路径名称 2. 从输入到结果的完整路径 3. 可验收的方式（追溯到哪条验收场景） 4. 涉及的字段和状态 先不要修改任何代码，也不要手动切分切片，只输出可验收路径清单。
🎯 预期输出：AI 输出了 2—3 条可验收路径，每条都有从输入到结果的完整路径和可验收方式，追溯到第三课契约。
Task 2：主管写本轮做什么和不做什么
本轮聚焦的可验收路径：【填写路径名称】 本轮做什么：【填写】 本轮明确不做：【填写，至少一条】 请复述你理解的本轮边界。在我确认前，不要开始实施。切分计划交给后续 Skill 自动完成。
🎯 预期输出：AI 复述了本轮边界，等待你确认后才实施。
Task 3：激活 Skill 自动生成 Plan（增量实施范式），主管核对后才授权 Execute
请使用 incremental-implementation 技能帮我规划实施。 本轮聚焦的可验收路径：【填写路径名称】 本轮边界：【填写】 本轮明确不做：【填写】 请自动把本轮需求切成 3—5 个独立步骤，写入 docs/LESSON_04_IMPLEMENTATION_PLAN.md。 每个步骤写清：修改的文件、涉及的字段和状态、验收路径。 先不要修改代码，只输出计划预览，等待我回复许可口令。
🎯 预期输出：Skill 自动生成计划并落盘 IMPLEMENTATION_PLAN.md，等待你的许可口令后才执行代码修改。
Task 4：实施一个可见变化，至少展示两种必要状态
授权执行 Step 1 请按计划实施 Step 1，只修改授权范围内的文件。 实施后报告：实际修改文件、验收方法、展示的状态。
🎯 预期输出：Agent 只在授权范围内修改；变化肉眼可见；至少两种状态可切换；技术状态和业务状态物理隔离。
Task 5：主管按契约验收，记录候选版本与处置结果
请按以下步骤完成验收与归档： 1. 逐项对照第三课验收场景，报告每条验收的通过或失败。 2. 如果通过，按项目约定保存实际版本证据，并记录主管处置；不固定提交数量。 3. 运行 git status 确认 working tree clean。 4. 如实报告实际运行过的工程检查和结果。未运行的不要声称通过。
🎯 预期输出：验收追溯到契约；候选实现与主管处置分别留痕（版本记录）；Working Tree 恢复 Clean；没有自动宣称通过。

2. 💡 常见概念误区与正确理解 (3 栏对照表)

常见误区 (Misconception) 正确硬核理解 (Correct Engineering Reality) 如何纠偏与护栏防护 (Remedy & Guardrails)
误区 1
"让 AI 一口气写完页面所有功能效率最高"		 一口气修改 10 个文件会导致 Working Tree 一片狼藉，报错时无法定位根因。用薄切片范式，每次只授权一个切片。 树立正确工程意识，严格遵循护栏规范。
误区 2
"静态编译通过就代表切片做对了"		 静态检查无法替代人工点击页面和主管对业务逻辑的验收。必须逐项对照第三课验收场景确认。 树立正确工程意识，严格遵循护栏规范。
误区 3
"混淆界面技术状态与业务流程状态"		 Loading 或 Error 是技术状态，待处理或已完成是业务状态。两者物理隔离，互不替代。 树立正确工程意识，严格遵循护栏规范。
误区 4
"Git 版本记录自动等于业务审批"		 源码修改和管理进度是两个维度的资产。用版本记录呈现实际变化，主管再依据验收证据作业务处置。 树立正确工程意识，严格遵循护栏规范。
误区 5
"验收不通过就让 AI 随便改到通过"		 验收不通过时记录问题而非强行通过；候选实现与主管处置分别留痕，不自动宣称通过。 树立正确工程意识，严格遵循护栏规范。

2. 🎯 课后退场自测题 (Exit Ticket)

❓ 退出门禁题 1：薄切片和把任务拆成技术碎片有什么区别？一条合格的薄切片从哪里到哪里完整？
参考答案解析：
薄切片是一次完成一条从输入到结果的纵向变化，有业务结果可验收；技术碎片没有业务结果。从输入到结果完整。
❓ 退出门禁题 2：Plan & Execute 要求主管在授权 Execute 前核对什么？为什么不能跳过核对？
参考答案解析：
核对字段、状态、修改范围和验收路径；跳过核对会让 Agent 自行决定范围，偏离契约。
❓ 退出门禁题 3：技术状态和业务状态有什么区别？各举一个例子。
参考答案解析：
技术状态：加载、空、错误、成功等界面呈现；业务状态：草稿、待处理、已完成等业务生命周期。例：Loading 是技术状态，待处理是业务状态。
❓ 退出门禁题 4：如何把验收场景、观察、证据、结论、责任和版本关联起来？
参考答案解析：
从验收场景链接操作、观察、原始证据、结论、责任和具体版本；候选实现与主管处置分别留痕，但提交数量不固定，Git 不等于业务审批。
❓ 退出门禁题 5：主管验收不通过时应该怎么处理？为什么不能自动宣称通过？
参考答案解析：
记录问题而非强行通过；导出 .patch 快照备份后恢复 Clean；候选实现与主管处置分别留痕。
三句话带走 (Key Takeaways)：
  1. 不要巨石盲开，用 `IMPLEMENTATION_PLAN.md` 把大需求切成连续薄切片。
  2. 记住版本控制与业务验收分工：版本记录事实，主管依据证据作业务处置。
  3. 代码改坏后先导出 `.patch` 快照，再按确认范围恢复 Clean。
