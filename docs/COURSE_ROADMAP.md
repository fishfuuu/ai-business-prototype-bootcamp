## 1. 课程定位与终局目标

### 核心定位

课程目标不是培养专业的 Vue/TypeScript 程序员，而是借助 Coding Agent（Claude Code / Codex），将各部门业务主管培养为“超级业务产品经理（Super Business PM）”。

学员默认无代码、Git、MCP 和终端命令行基础，但熟悉本部门流程、指标、风险与决策。主管不需要去搞底层的生产服务器运维、复杂并发代码或手打 Git/Patch 命令行，而是要掌握：
1. **高保真原型控盘能力**：在 2 小时内用自然语言 + AI 跑出可运行、可点击、带模拟数据的高保真原型系统。
2. **需求与数据契约表达能力**：将口头需求标准化为《业务功能卡》、可视化数据契约卡与明确的输入/输出边界。
3. **工程防护与版本证据管理能力**：掌握安全沙箱授权、`CLAUDE.md` 护栏、Grounding (事实锚定)、三分记忆模型（工作记忆、外部长期记忆、版本证据）与版本恢复流程，防止项目失控。
4. **可复核证据驱动的验收与审查能力**：基于可复核、可重复生成的四类证据卡片（视觉、行为、工程、范围）完成验收，并在独立审查上下文隔离下依据《CEO 3 大决策树》（本课程主管处置框架，非代码运行时硬控制，亦非行业通用标准拓扑）引导 Codex 进行代码审查与一票裁决。
5. **确定性与概率性逻辑切割能力**：准确判断普通功能（确定性规则）与 AI 功能（概率性生成），坚持 HITL 人工确认，在结业时输出《产品决策与开发启动包》（明确声明非生产就绪系统，供 IT 开始正式设计与开发，而非直接上线）。

### 三层能力成熟度模型 (Three-Layer Maturity Model)

训练营帮助主管实现三层 AI 协作能力跨越：
- **第一层：Prompting (单次指令)** —— 通过单次指令描述任务，理解裸 Prompt 局限。
- **第二层：Harness Engineering (工程护栏)** —— 通过规则 (`CLAUDE.md`)、文件 (`PROJECT_STATE.md`)、Skills (`grill-me`, `design-lint`)、权限与工作流约束 Agent 执行；`verify-project.ps1` 仅作母仓库遗留维护检查，不作为课堂或业务通过证明。
- **第三层：Bounded Agent Loop (受控 Agent 循环)** —— 在明确目标、边界、工具、风险和停止条件下，让 Agent 进行受控自主循环，主管在关口依据决策树行使人在回路 (HITL) 盖章。

### 教学设计与概念解析四步范式 (Pedagogical 4-Step Formula)

为解决概念浮于表面与比喻失真问题，全课程所有硬核概念（LLM, Tools, Agent, ReAct, Tokens, MCP, Git, Linters）统一执行**【四步概念解析公式】**（每课最多 2–3 个“必须掌握”概念，单概念讲解控制在 3–5 分钟，且必须包含最小完整解释）：
1. **硬核工程定义 (Engineering Definition)**：使用标准的 IT/软件工程术语，讲清工程本质，明确“是什么”与“不是什么”。
2. **底层运作机制 (Underlying Mechanism)**：解释代码、内存、接口或数据在底层的实际流转逻辑。
3. **具象业务比喻与反例 (Business Metaphor & Negative Example)**：建立大脑记忆锚点并提供反例澄清（如：把 Git 双 Commit 比喻为“两阶段版本记录：Excel 表格草稿录入 (Commit A 源码草稿) 与 部门主管签字盖章确权 (Commit B 业务确权)”，同时注明 Git 本身不理解业务审批，也不自动形成授权控制；把 TS 类型契约比喻为“业务表单必填字段规范卡”）。
4. **IT 沟通与交接价值 (Handoff Value)**：明确该概念对应学员**刚完成的哪一步实操**，以及主管为何需要用该词与 IT 沟通或作出判断。

### 训练营支持的三类业务原型与 Mock 机制

训练营全课程持续贯穿支持三类典型业务原型，学员从 L1 起持续发展自己的部门原型：
1. **A. 监控与决策型**：适合经营分析、异常监控、投产分析、履约预警（看指标 -> 看异常 -> 下钻明细 -> 做出决策）。
2. **B. 任务与流程型**：适合预算申请、退货处理、工单派发、单据审批（创建记录 -> 处理任务 -> 状态流转 -> 推进下一步）。
3. **C. 操作工具型**：适合文案生成、规则计算、数据整理、格式转换（输入 -> 规则处理 -> 结果输出 -> 人工确认/复制/导出）。

**教师演示与学员原型边界**：
- 教师十课统一演示案例：“业务异常预警与闭环处置工作台”。
- 学员从 L1 开始持续发展自己部门的业务原型。
- 普通学员默认使用 Mock 数据；教师在受控环境下演示真实模型/API调用。学员无需配置 API Key 或 MCP。
- **Mock 职责分工**：
  1. **主管**：定义字段、含义、枚举、范围和流程规则，并验证业务合理性。
  2. **课程团队**：提供模板与安全规则。
  3. **Agent**：起草明确标记的合成数据。
  4. **教师/助教**：检查确认无真实敏感数据。

## 3. 工具分工与角色契约

### 1. Claude Code（主要实施者 / 开发 Agent）
- 需求解构与方案推演
- 页面与组件增量创建
- 执行 **ReAct 范式**、**Plan & Execute 范式** 与 **Subagent 调度**
- 本地调试与自测验证（学员：Verifier Subagent 或本课规定的验证方式；维护者：`verify-project.ps1` 仅作母仓库遗留维护检查，不作为课堂或业务通过证明）

### 2. Codex（独立审查者 / 审计 Agent）
- 从第 8 课开始正式引入（基于独立审查上下文隔离规则）
- **独立审查上下文隔离**：新建只读独立会话，仅调取已确认需求、稳定 Commit 与 Candidate Commit 的版本变更
- 审查隐患、逻辑越界与未授权的范围修改，只读不修改代码
- 提供自然语言审计意见（阻断/重要/建议）

### 3. 主管（最终裁决者 / 人在回路盖章官 / 中央调度系统）
- 掌控 Workflow 推进阶段
- 行使 Keep / Omit / Remove / Modify 裁决权
- 对 Codex 审查意见做出 4 种决定：接受、拒绝、延期、超出本次范围
- **依据《CEO 3 大决策树》**（主管处置框架）签署人在回路 (HITL) 授权，完成最终业务验收

## 4. 高阶工程防错 8 大防护规则 (Robustness & Patch Rules)

为防止教学实操中出现卡死、白屏、死循环和弹窗风暴，全课程严格注入 8 大高阶防错机制：

1. **Subagent 超时熔断规则 (Subagent Lifecycle & Timeout Rule)**：
   派发给子智能体（如静默测试 Subagent）的独立任务必须明确设置超时与停止条件（如 `DurationSeconds: 60`），超时自动释放，决不挂起主 Agent。
2. **Subagent 预授权与只读沙箱规则 (Subagent Read-only Sandbox Rule)**：
   静默后台运行的 Subagent 仅继承只读工具权限 (Read-only Tools)，写权限修改动作必须返回主 Agent 界面由主管签署 HITL 口令确认。
3. **Subagent 产物强制磁盘落盘规则 (Disk Persistence Rule)**：
   Subagent 产出的所有测试截图、DOM 操作日志与检查报告，必须写入本地磁盘目录（`local-backups/`）与 `PROJECT_STATE.md`，决不随 Context 重置而蒸发。
4. **双 Agent 两轮仲裁门禁 (2-Round HITL Arbitration Rule)**：
   第 8 课开发 Agent 与只读审查 Agent 辩论超过 2 轮时，强制阻断自动循环，引发主管 CEO 仲裁盖章。
5. **Mock 数据降级保护桥梁 (Mock Fallback Bridge)**：
   第 9~10 课真 AI 接口连接失败、网络超时或非法返回时，降低调用失败导致页面不可用的风险，显示降级来源并降级回 Mock Data 结构化渲染。
6. **有界排错护盾与 2 轮熔断恢复 (Bounded Debugging & Rollback Protocol)**：
   第 6 课排错严格限定在“界面呈现与业务契约不一致”的领域，严禁主管手打 Git/Patch 命令或深挖底层代码；同一 Bug 最多由 Agent 自修 2 轮，超过两轮后停止自动修改，保留诊断证据，并由教师或助教恢复到已确认基线。（注：自动恢复脚本为待实现教学资产，当前不作为课堂通过条件）。
7. **独立上下文审查与 CEO 3 大决策树 (Context-Isolated Audit & Decision Tree)**：
   第 8 课 Codex 必须在全新的只读独立会话中开启，只读取 Candidate Commit 的版本变更；若双 Agent 辩论满 2 轮未达成一致，主管依据《CEO 3 大决策树》（业务优先/安全红线/范围防漂移，作为主管处置框架）行使一票裁决权。
8. **确定性/概率性切割与业务自动化红线 (Deterministic vs. Probabilistic Cut Rule)**：
   计算与状态流转由确定性代码执行；智能生成由 LLM 执行且须经过 HITL 确认；编写《业务自动化红线清册》排除高危业务。

### 10 节课共同规则（统一的“每课结束动作”）

从第二课起，每节课结束前必须固定执行以下 5 个管理动作：

```text
每课结束固定执行：
1. 更新 docs/PROJECT_STATE.md (更新业务事实与会话摘要)
```

### 第 6 课：学会定位和修复问题 — 五层诊断卡与有界排错护盾

### 第 8 课：Claude Code 开发，Codex 独立审查 — 上下文隔离与 CEO 3 大决策树
* **定位**：**独立审查上下文隔离**，新建只读会话审计 Candidate Commit，注入《CEO 3 大决策树》解锁高维裁决；六种 Agent 协作模式作为主管决策框架比较选型。
* **主要内容**：
  1. 新建独立只读审查会话，消除开发 Agent 的历史思考污染；默认工具不可用时改用隔离的新审查会话，不得跳过审查，也不得把同一实现会话改名为审查。
  2. Codex 审查 Candidate Commit 的 Diff，仅输出自然语言审计意见（阻断/重要/建议），严禁修改代码。
  3. **双 Agent 仲裁与 CEO 3 大决策树**：辩论超过 2 轮强行挂起，主管依据决策树（主管处置框架）执行裁决：
     - **规则 A（业务优先）**：代码重构提案，功能无影响 ➔ `[延期]`
     - **规则 B（安全红线）**：敏感数据未脱敏或数据契约破损 ➔ `[接受并打回修改]`
     - **规则 C（防范围漂移）**：无关功能扩充提案 ➔ `[超出本次范围]`
  4. **六种 Agent 协作模式选型框架**：调度者—执行者、顺序流水线、上下文隔离独立审查三种深讲/演示；并行扇出—汇总、对等协作、人机协作仲裁三种识别/比较。六种模式是本课程主管决策框架，不是行业唯一标准，不要求学员实现六套工程系统。

### 第 9 课：业务 Agent 场景判断与产品设计 — 逻辑切割与 Mock 降级保护桥梁
* **定位**：确定性规则 vs. 概率性生成逻辑切割、AI 隐私边界、开发工具链 / 业务 API / 模型 API 三链区分与 Mock 降级保护桥梁。
* **主要内容**：
  1. **确定性 vs. 概率性逻辑切割**：计算与状态流转由确定性代码执行；智能生成由 LLM 执行并经过 HITL 确认。
  2. **三链区分**：开发工具链处理开发期文件/浏览器/验证工具；业务 API 链连接产品与业务服务；模型 API 链连接受控服务与模型。三链分别描述调用者、凭证、数据、失败和 owner，MCP 不与后两链混称。
  3. **真实调用边界**：教师真实模型/API 调用完全位于仓库外受控教师环境，屏幕只展示脱敏输入输出；学员全程使用 Mock，不获得 Key、服务配置或可复用凭证。
  4. **Mock 降级保护桥梁 (Mock Fallback Bridge)**：真实 API 失败或超时时，降低调用失败导致页面不可用的风险，显示降级来源，自动降级渲染 L03 静态 Mock Data。

* **主要内容**：
