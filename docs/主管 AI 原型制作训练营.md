    # 主管 AI 原型制作训练营

    ## 一、课程目标

    课程目标不是培养程序员，也不是直接开发复杂 AI Agent，而是让运营主管能够：

    1. 使用 Claude Code 从零创造自己想要的业务系统页面。

    2. 用自然语言和参考截图持续修改系统。

    3. 使用 Skills 提高需求分析、页面设计、调试和验证的稳定性。

    4. 掌握少量必要的工程化习惯，防止项目越改越乱。

    5. 使用 Codex 独立审查 Claude Code 的成果。

    6. 判断页面中哪些环节适合普通功能、AI 功能或 AI Agent。

    7. 完成一个带简单 AI 能力的业务系统 Demo。

    8. 将经过验证的业务方法沉淀为可复用 Skill。

    课程主线：

    ```Plain Text
    从零创造系统
    → 做成自己想要的样子
    → 学会稳定控制 Agent
    → 跑通真实业务流程
    → 找到 AI 融入位置
    → 沉淀业务方法
    ```

    ---

    # 二、课程工具

    ## Claude Code

    作为主要制作工具，负责：

    - 理解业务需求

    - 从零创建页面

    - 根据截图调整页面

    - 实现业务功能

    - 定位和修复问题

    - 启动项目并完成自测

    - 编写项目说明

    ## Codex

    从第七课开始作为独立评审工具，负责：

    - 检查 Claude Code 是否误解需求

    - 检查是否超出修改范围

    - 实际操作页面完成验收

    - 检查明显的业务和页面问题

    - 审查 AI 功能的输入、输出和人工确认机制

    固定协作方式：

    ```Plain Text
    Claude Code 实现
    → Claude Code 自测
    → Codex 独立审查
    → Claude Code 修复确认的问题
    → 运营主管验收
    ```

    # 四、第一课的“从零开始”定义

    第一课从零开始创造业务系统，但不从零搭技术环境。

    ## 学员从零决定的内容

    - 系统名称

    - 系统解决的问题

    - 目标使用者

    - 菜单结构

    - 首页内容

    - 指标和业务字段

    - 页面布局

    - 需要重点关注的异常

    - 页面中的操作入口

    ## 提前准备的技术底座

    ```Plain Text
    可直接运行的空白前端工程
    基础路由
    通用组件库
    空白首页
    模拟数据目录
    统一启动脚本
    Git初始版本
    Claude Code和Codex基础规则
    ```

    技术底座中不预置具体运营页面和业务流程。

    课程原则：

    > 从零创造业务系统，但不让学员把时间消耗在安装环境和解决依赖问题上。

    # 六、详细课程内容

    ## 第1课：从业务问题创建第一个系统页面

    ### 核心目标

    第一节课结束时，学员不仅能够做出按自己业务想法创造出的系统页面，还能理解并复述 **LLM、Tools、Agent、ReAct 与 Workflow** 在系统制作中的作用。

    > 轻量建立 AI Agent 基础概念，学会用 Workflow 确认卡口控制 Agent，但不引入复杂框架源码、Git 或 API 开发。

    ### 课堂准备

    IT提供一个可以直接运行的空白工程。

    打开后只有：

    - 空白系统框架

    - 空白首页

    - 基础组件

    - 模拟数据能力

    - 一键启动入口

    不预制经营看板、商品列表或运营流程。

    ### 课堂步骤

    #### 第一步：描述想要的系统

    让学员回答：

    - 这个系统叫什么？

    - 谁使用？

    - 最想解决什么问题？

    - 每天打开后首先想看到什么？

    - 哪些异常必须立即看到？

    - 最希望减少哪一种重复工作？

    #### 第二步：让 Claude Code 提出第一版结构

    示例：

    ```Plain Text
    我要从零制作一个运营主管使用的业务系统。

    这个系统暂定名为“商品经营工作台”。

    主要使用者是运营主管。
    他需要查看各渠道、店铺和商品的目标完成情况，
    快速发现异常，并跟进运营动作。

    请先不要修改代码。

    请提出：
    1. 系统菜单结构
    2. 首页的信息层级
    3. 首页最重要的指标
    4. 应该重点展示的异常
    5. 第一版应该包含哪些页面
    6. 哪些内容暂时不做

    保持第一版简单，使用模拟数据。
    ```

    #### 第三步：学员选择和修改方案

    学员不是接受 Claude Code 的全部建议，而是决定：

    - 删除哪些菜单

    - 哪些指标不重要

    - 哪些业务术语不准确

    - 哪些内容必须突出

    - 第一版到底做几个页面

    #### 第四步：Claude Code 开始制作

    第一课只制作：

    - 系统名称

    - 左侧菜单

    - 一个首页

    - 一个核心业务模块

    - 一套模拟数据

    #### 第五步：连续修改三次

    例如：

    - 调整指标顺序

    - 增加一个主管真正关心的模块

    - 删除无价值内容

    - 改变首页信息层级

    ### 工程化内容

    只强调两条：

    1. 第一版只使用模拟数据。

    2. 先完成可运行版本，不追求完整系统。

    ### 课堂成果

    - 一个从空白业务工程创建出来的系统雏形

    - 系统名称和菜单

    - 一个可运行首页

    - 一个核心业务模块

    - 至少三次由学员主动提出的修改

    ### 课后作业

    增加一个自己每天真正想看的模块。

    ### 通过标准

    学员能够说明：

    - 系统为什么这样设计

    - 哪些内容来自自己的业务判断

    - 下一步最想增加什么

    ## 第2课：用参考图做出像样的企业页面

    ### 核心目标

    让学员学会使用参考图、现有系统和草图控制页面效果，而不是只说“做得好看一点”。

    ### 使用 Skill

    ```Plain Text
    frontend-design
    ```

    ### 课堂内容

    第二课由于包含基础 Git 存档，时间分配需严格控制。

    #### 任务1：提取结构与基线存档（18分钟）
    1. 检查 Git 状态（必要时 `git init`）。
    2. 提交第一课稳定版本与 `PROJECT_STATE.md`。
    3. 让 Claude Code 分析脱敏截图的信息层级和区域划分。

    #### 任务2：规范映射（20分钟）
    根据 `DESIGN.md` 将结构映射到项目已有的组件和 Token（不虚构颜色）。

    #### 任务3：视觉裁决与修改（35分钟）
    学员决定 Keep / Omit / Remove / Modify，使用 `frontend-design` 完成重构。

    #### 任务4：对比验证与成果存档（17分钟）
    1. 运行验证，保存试衣镜截图。
    2. 提交第二课版本 (`git commit`)。
    3. 查看前后变化 (`git diff`)。

    示例：

    ```Plain Text
    请使用 frontend-design。

    参考截图中的信息层级和布局，
    但不要照搬品牌、颜色和具体内容。

    这是运营主管使用的企业内部系统，
    重点是快速识别异常和完成管理动作，
    不是营销网站。

    保留：
    - 顶部核心指标
    - 中间趋势区域
    - 底部异常明细

    替换为：
    - 销售目标
    - 实际销售
    - 完成率
    - 同比
    - 环比
    - 异常状态

    不要增加夸张动画、渐变背景和装饰性元素。
    ```

    ### 工程化内容

    1. 引入 `DESIGN.md`。
    2. 引入 Git 基础（游戏存档概念），只教：`status, init, add, commit, log, diff`。不涉及 GitHub 或分支。

    让学员理解：

    ```Plain Text
    DESIGN.md
    不是一次提示词，
    而是整个项目长期遵守的页面设计规则。
    ```

    内容包括：

    - 页面风格

    - 字体和间距

    - 状态颜色

    - 卡片和表格规范

    - 禁止使用的效果

    - 企业系统设计原则

    ### 课堂成果

    - 一个经过截图参考和 Skill 优化的页面

    - 一份基础 `DESIGN.md`

    - 一份简单设计取舍说明

    ### 课后作业

    选择一个熟悉的系统页面，制作自己的运营版本，并记录：

    - 保留了什么

    - 删除了什么

    - 增加了什么

    - 为什么这样调整

    ### 通过标准

    页面已经转化为自己的业务系统，而不是简单照抄截图。

    ## 第3课：让 Agent 帮助自己想清楚需求

    ### 核心目标

    让学员从“我有一个大概想法”，走到“Agent可以稳定执行”。

    ### 使用 Skill

    ```Plain Text
    grill-me
    ```

    ### 课堂内容

    从一个模糊需求开始：

    ```Plain Text
    我想增加一个商品运营管理页面。
    请使用 grill-me 帮我逐步想清楚。
    一次只问一个最重要的问题。
    ```

    `grill-me`重点追问：

    - 谁使用？

    - 主要工作是什么？

    - 页面首先应该看到什么？

    - 需要完成什么操作？

    - 哪些情况属于异常？

    - 哪些字段必须准确？

    - 本次不做什么？

    - 怎样判断功能完成？

    最后形成简化业务功能卡：

    ```Plain Text
    功能名称
    目标使用者
    业务问题
    页面内容
    核心操作
    关键规则
    本次范围
    暂不处理
    验收标准
    ```

    ### 工程化内容

    引入**数据契约设计**与**验收设计**：

    1. **轻量数据契约卡**：明确字段名称、业务含义、数据类型、是否必填、数据来源、敏感等级等。
       - *监控决策型*需补充：指标口径、对比基准、异常阈值。
       - *任务流程型*需补充：角色、允许动作、状态迁移。
       - *操作工具型*需补充：输入校验、输出结构、失败状态。
    2. **验收标准前置**：完成必须可以通过页面操作验证，从这里开始定义验收条件。

    ### 课堂成果

    一份可以直接交给 Claude Code 实现的业务功能卡。

    ### 课后作业

    选择一个真实业务功能，使用 `grill-me` 完成需求梳理。

    ### 通过标准

    没有参与讨论的人只看功能卡，也能基本理解要做什么。

    ## 第4课：把大需求拆成连续的小成功

    ### 核心目标

    避免 Agent 一次修改太多，导致页面跑偏、问题难定位、学员失去控制。

    ### 使用 Skill

    ```Plain Text
    incremental-implementation
    ```

    ### 课堂内容

    将一个大需求：

    ```Plain Text
    增加完整的店铺运营管理功能。
    ```

    拆成：

    ```Plain Text
    1. 增加店铺目标列表
    2. 增加店铺详情
    3. 增加异常原因记录
    4. 增加运营动作填写
    5. 增加主管点评
    ```

    示例：

    ```Plain Text
    请使用 incremental-implementation。

    我要实现“异常原因记录”功能。

    先把需求拆成可以独立完成和验证的小步骤。
    暂时不要修改代码。

    每一步需要说明：
    1. 目标
    2. 修改范围
    3. 完成标准
    4. 验证方式
    5. 对现有页面的影响
    ```

    每完成一步：

    1. 运行页面。

    2. 实际操作。

    3. 检查结果。

    4. 保存稳定版本。

    5. 再继续下一步。

    ### 工程化内容

    建立固定流程与**数据接口意识**：

    1. 步步推进：需求 → 拆分数据结构 → 画空壳页面 → 连起来 → 验证 → `git commit` 保存一步。
    2. 页面状态意识：真实数据未来由API提供，必须至少实现四种页面状态（Loading 正在获取、Empty 没有数据、Success 正常显示、Error 获取失败）。坚持 Mock，不接真实后端。

    ### 课堂成果

    一个由三至五个步骤完成的业务功能。

    ### 课后作业

    拆解下一个功能，只实现第一步并完成验证。

    ### 通过标准

    每一个步骤都可以独立说明目标和完成结果。

    ## 第5课：建立不会轻易失控的项目

    ### 核心目标

    让学员理解最少但必要的工程纪律。

    本课不新增 Skill。

    ### 课堂内容

    建立六条规则：

    1. 一次只处理一个明确目标。

    2. 修改前必须确认范围。

    3. 不允许 Agent 自行更换技术框架。

    4. 不允许未经确认增加依赖。

    5. 修改后必须运行并验证。

    6. 稳定版本保存后才能继续修改。

    介绍核心护栏文件：

    ```Plain Text
    CLAUDE.md
    Claude Code长期遵守的项目规则，定义依赖、密钥、改动范围等安全护栏。
    ```
    （注：`AGENTS.md` 将在第8课引入）

    介绍三个版本概念：

    ```Plain Text
    Git commit
    正式的存档与恢复手段（查看历史、比较版本、恢复稳定提交）

    Checkpoint脚本
    教师提供的紧急保底工具（仅在Git恢复失败时使用）
    ```

    不要求学员学习复杂Git命令。

    ### 每次完成后的固定报告

    ```Plain Text
    1. 修改了哪些文件
    2. 每个文件修改了什么
    3. 哪些内容保持不变
    4. 执行了哪些验证
    5. 验证结果是什么
    6. 还有哪些内容没有验证
    ```

    ### 课堂成果

    - 简化版 `CLAUDE.md`

    - 简化版 `AGENTS.md`

    - 基础 `DESIGN.md`

    - 一个稳定 Git 保存点

    - 一次完整修改和验证记录

    ### 课后作业

    尝试一种明显不同的页面方案，决定保留或回退，并说明理由。

    ### 通过标准

    学员能解释如何避免 Agent 越改越乱。

    ## 第6课：学会定位和修复问题

    ### 核心目标

    让学员不再害怕错误，也不让 Agent 盲目尝试修改。

    ### 使用 Skill

    ```Plain Text
    diagnosing-bugs
    ```

    ### 课堂内容

    使用问题报告卡：

    ```Plain Text
    问题位置
    操作步骤
    实际结果
    预期结果
    是否可以稳定复现
    影响范围
    截图或错误信息
    本次修复限制
    ```

    示例：

    ```Plain Text
    请使用 diagnosing-bugs。

    当前问题：
    在商品详情页面点击“保存运营动作”后，
    弹窗关闭了，但页面没有显示新记录。

    预期：
    保存后，新记录应立即出现在运营动作区域。

    请先：
    1. 复现问题
    2. 收集证据
    3. 定位根因
    4. 提出最小修复方案

    暂时不要修改代码。
    不要重构其他页面。
    ```

    固定调试顺序：

    ```Plain Text
    复现
    → 收集证据
    → 提出假设
    → 验证假设
    → 最小修复
    → 重新验证
    ```

    ### 工程化内容

    采用**五层诊断卡**定位问题（不再粗暴分为UI/API）：

    1. **页面与样式层**：布局错位、颜色错误
    2. **组件与状态层**：点击无反应、数据不同步
    3. **路由与页面层**：页面打不开、白屏
    4. **数据与接口层**：无数据、字段不一致、请求失败
    5. **环境与依赖层**：启动失败、构建失败

    强调：
    - 没有复现，不应直接修改；定位层级后才能给出最小修复方案；修复后必须做回归测试验证。

    ### 课堂成果

    成功定位并修复一个真实页面问题。

    ### 课后作业

    提交一份问题报告和修复前后证据。

    ### 通过标准

    学员能够清楚描述问题，而不是只说“页面坏了”。

    ---

    ## 第7课：让 Agent 实际操作页面完成验收

    ### 核心目标

    让学员理解：

    > 代码写完不代表功能完成，必须真实操作页面。
    >
    >

    ### 使用 Skills

    Claude Code：

    ```Plain Text
    webapp-testing
    ```

    Codex：

    ```Plain Text
    playwright-interactive
    ```

    ### 课堂内容

    选择一条完整业务流程：

    ```Plain Text
    进入经营总览
    → 找到异常店铺
    → 查看店铺详情
    → 填写运营动作
    → 保存
    → 确认记录展示
    ```

    先由 Claude Code 自测：

    ```Plain Text
    请使用 webapp-testing。

    启动当前系统并实际操作以下流程：

    1. 打开经营总览
    2. 找到一条异常店铺
    3. 进入店铺详情
    4. 填写运营动作
    5. 点击保存
    6. 确认记录是否正确展示

    请记录：
    - 每一步的实际结果
    - 页面错误
    - 控制台错误
    - 截图证据
    - 未通过项目

    暂时不要修复。
    ```

    再由 Codex 使用 `playwright-interactive` 独立验证相同流程。

    ### 工程化内容

    引入“四类验收证据”：

    - **视觉证据**：前后截图
    - **行为证据**：操作结果或测试记录
    - **工程证据**：Verify / Typecheck / Build 通过
    - **范围证据**：Git Diff / Commit

    ### 课堂成果

    一份由 Claude Code 和 Codex 分别完成的页面验收记录。

    ### 课后作业

    找一名同事在没有口头说明的情况下使用 Demo，记录两个主要问题。

    ### 通过标准

    至少一条真实业务流程通过页面操作验证。

    ## 第8课：Claude Code 开发，Codex 独立审查

    ### 核心目标

    建立明确的双 Agent 分工，而不是让两个 Agent 同时随意修改。

    ### 使用 Skill

    Codex：

    ```Plain Text
    code-review-and-quality
    ```

    ### 课堂内容

    由 Claude Code 实现一个完整动作，例如：

    - 主管点评

    - 指派负责人

    - 提交运营复盘

    - 设置商品目标

    - 标记异常原因

    Claude Code完成：

    ```Plain Text
    实现
    → 自测
    → 报告修改范围
    → 提供验证证据
    ```

    Codex独立审查：

    ```Plain Text
    请使用 code-review-and-quality。

    不要修改代码。

    请独立审查当前未提交修改。

    需求目标：
    增加“主管点评”功能。

    重点检查：
    1. 是否完成需求
    2. 是否误改其他页面
    3. 页面操作是否完整
    4. 是否存在明显业务错误
    5. 是否完成真实验证
    6. 是否出现超出范围的改动

    审查结果分为：
    - 阻断
    - 重要
    - 建议
    ```

    Claude Code只处理经过学员确认的阻断和重要问题。

    ### 工程化内容

    明确职责与 `AGENTS.md`：

    引入 `AGENTS.md` 作为 Codex 审查规则。

    ```Plain Text
    Claude Code
    主要实施者（实现和自测）

    Codex
    独立审查者（基于 Commit/Diff 提供独立意见，并非甲方）

    运营主管
    最终裁决者（决定接受、拒绝、延期或判定超出范围）
    ```

    学员必须判断：

    - Codex说的问题是否真实存在

    - 是否值得本期修复

    - 是否属于以后优化

    - 是否超出当前范围

    ### 课堂成果

    完成一轮：

    ```Plain Text
    实现
    → 自测
    → 独立审查
    → 判断
    → 修复
    → 最终验收
    ```

    ### 课后作业

    让 Codex 审查现有 Demo，选择两个真正重要的问题交给 Claude Code 修复。

    ### 通过标准

    学员不会机械接受所有 Agent 建议。

    ## 第9课：判断系统中哪些位置适合加入 AI

    ### 核心目标

    理解普通功能、AI功能和AI Agent的区别。

    本课不实现复杂 Agent。

    ### 三类能力

    #### 普通系统功能

    适合：

    - 固定规则计算

    - 查询筛选

    - 数据保存

    - 审批状态

    - 权限控制

    - 明确规则判断

    #### AI功能

    适合：

    - 总结

    - 分类

    - 信息提取

    - 内容解释

    - 草稿生成

    - 建议生成

    #### AI Agent

    适合：

    - 根据条件自动启动

    - 连续读取多个数据源

    - 调用多个工具

    - 推进多个步骤

    - 等待人工确认后继续

    ### 课堂分析方法

    逐页检查现有 Demo：

    1. 哪些内容需要阅读大量数据？

    2. 哪些内容需要重复总结？

    3. 哪些字段需要从文字中提取？

    4. 哪些内容经常从零开始填写？

    5. 哪些判断依赖经验？

    6. AI出错后是否容易被人发现？

    7. 是否必须人工确认？

    建立 AI 机会卡：

    ```Plain Text
    页面
    当前人工动作
    输入数据
    AI可以完成的任务
    输出格式
    人工确认方式
    错误风险
    失败处理
    不允许AI执行的动作
    ```

    ### 工程化内容

    严格定义 **AI 安全边界与 HITL (Human-in-the-loop)**：

    - **数据契约与隐私**：输入是什么，哪些敏感数据绝不发送给AI。
    - **结构化输出**：AI 返回必须是固定结构草稿。
    - **人类确认门槛**：未确认前不进入正式流程，AI 不得直接执行修改业务数据的动作（如直接扣库存）。

    ### 课堂成果

    - 三个AI机会

    - 一个优先实现目标

    - 一份完整AI机会卡

    ### 课后作业

    准备：

    - 示例输入

    - 理想输出

    - 错误输出

    - 人工修改示例

    - 确认规则

    ### 通过标准

    选中的场景输入明确、输出可检查、错误可人工纠正。

    ---

    ## 第10课：落地有限AI功能与IT交接

    ### 核心目标

    完成从普通业务系统到带AI能力Demo的第一次升级。

    ### 使用 Skill

    ```Plain Text
    skill-creator
    ```

    ### 推荐实现的AI功能

    > 根据页面上的经营指标和运营补充说明，生成问题分析和下一步动作草稿。
    >
    >

    ### 页面流程

    ```Plain Text
    页面准备明确数据
    → 用户点击“AI生成分析”
    → AI返回结构化草稿
    → 用户人工编辑
    → 用户确认
    → 保存为正式内容
    ```

    ### 功能要求

    - 明确展示AI输入范围

    - AI返回固定结构

    - 显示生成状态

    - 提供失败提示

    - 输出可以人工编辑

    - 未确认前不进入正式流程

    - AI生成内容有明确标识

    - 不允许AI直接修改关键业务数据

    ### 结构化输出示例

    ```Plain Text
    异常概述
    可能原因
    影响判断
    建议动作
    需要补充的信息
    风险提示
    ```

    ### 可选：封装业务Skill

    （注：Skill 是加速工具，非结业强制前提，不占用必修时间。）
    使用 `skill-creator`，将课程中验证稳定的提示词封装为可复用 Skill。

    例如：

    ```Plain Text
    operation-exception-design
    ```

    该Skill负责：

    ```Plain Text
    1. 确认分析对象
    2. 确认指标和业务口径
    3. 确认异常判断条件
    4. 确认使用者和页面
    5. 确认需要的业务动作
    6. 判断普通功能和AI功能
    7. 确认人工审核位置
    8. 输出功能说明和验收标准
    ```

    示例指令：

    ```Plain Text
    请使用 skill-creator。

    我要创建一个名为 operation-exception-design 的Skill。

    这个Skill用于帮助运营主管设计异常分析页面。

    它应该逐步确认：
    - 分析对象
    - 指标口径
    - 异常条件
    - 页面使用者
    - 页面内容
    - 运营动作
    - AI辅助环节
    - 人工确认环节
    - 验收标准

    每次只问一个关键问题。
    最终输出一份可以交给Claude Code实现的功能卡。
    ```

    ### 工程化内容

    让学员理解：

    - Prompt是系统资产，不应散落在页面代码里。

    - AI输入必须受到控制。

    - AI输出应尽量结构化。

    - 人工确认是正式工作流的一部分。

    - Demo负责验证价值。

    - IT负责正式数据、权限、安全、部署和系统集成。

    ### 课堂成果

    完成一个最小 AI 闭环（有限输入 → 处理 → 结构化草稿 → 人工确认 → 兜底）。
    
    输出最终交付物：**IT 原型交接包**（最低包含：业务目标、用户角色、页面流程、字段状态、数据来源、AI输入输出、人工确认点、安全权限、验收场景、未实现项）。

    ### 结业演示

    学员进行10分钟演示：

    1. 系统解决什么业务问题。

    2. 第一课如何从零创造系统。

    3. 如何使用 `frontend-design` 优化页面。

    4. 如何使用 `grill-me` 澄清需求。

    5. 如何使用 `incremental-implementation` 分步实现。

    6. 如何使用 `diagnosing-bugs` 定位问题。

    7. Claude Code和Codex如何分工。

    8. AI为什么放在当前环节。

    9. 创建的业务Skill解决什么问题。

    10. 哪些部分需要IT工程化。

    # 七、每课固定结构与结束动作

    ## 每课结束动作

    为了确保课程连续性和工程交付，从第二课起，每课结束前必须固定执行以下动作：

    1. **更新状态**：更新 `docs/PROJECT_STATE.md`
    2. **运行验证**：运行本课自动化或人工验证
    3. **对比差异**：查看 `git diff` 确认修改范围
    4. **保存版本**：提交本课稳定版本 (`git commit`)
    5. **交接输入**：记录下一课的明确输入
    
    每周建议90分钟

    每周建议90分钟：

    ```Plain Text
    10分钟：展示本课可以完成的成果
    15分钟：老师演示本课方法或Skill
    45分钟：学员在自己的项目中实际操作
    10分钟：运行验证或Codex审查
    10分钟：保存成果并布置作业
    ```

    原则：

    - 理论讲解不超过25分钟。

    - 每次课至少一半时间由学员亲自操作。

    - 每节课必须产生肉眼可见的变化。

    - 作业控制在30—45分钟。

    - 每次作业只提交一个明确成果。
